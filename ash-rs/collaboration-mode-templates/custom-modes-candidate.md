# 自定义模式候选

状态：候选，暂不实现，也未安排实施。目标是创建一份模式定义和对应 prompt，后端加载后注册到模式目录，桌面端与 TUI 自动提供选择。普通模式共用现有执行系统，不需要为每个模式新增执行器。

当前产品仍只支持五种内置模式，使用 `CollaborationMode` 强类型表示；模式目录、自定义定义和动态注册均尚未实现。当前事实见 [五种模式](collaboration-modes.md)。

## 候选目标

让用户保存可重复使用的任务处理方式，例如代码审查、故障调查或文档整理。新增普通模式只需模式定义与 prompt；已有运行能力通过统一规则使用。桌面端和 TUI 读取同一份后端模式目录，命令、请求和历史通过稳定 ID 标识模式；改名、翻译或更换颜色不改变模式身份。

自定义模式与 Role、模型、推理强度、权限策略分别选择。模式定义任务的处理方式，Role 定义 Agent 的职责和能力上限，权限策略决定具体动作能否执行。

## 身份与定义

候选设计采用 `ModeId` 与模式定义目录。内置模式保留 `agent`、`plan`、`debug`、`multitask`、`ask` 五个 ID；自定义 ID 带来源命名空间，创建后保持不变，避免不同来源覆盖同一个模式。显示名称可以修改，也可以本地化。

| 内容 | 候选职责 |
| --- | --- |
| `ModeId` | 命令、请求、队列和历史中的稳定身份 |
| 模式定义 | ID、名称、说明、prompt 资产与修订版本，以及需要明确选择的运行选项 |
| Prompt | 调查步骤、任务组织、证据要求和交付方式 |
| 运行选项 | Goal 续接、工作流处理和子任务模式等有限、强类型的规则 |
| 模式目录 | 由后端解析、校验并提供可用定义，供各客户端读取 |
| 内置名称的本地化、颜色、显示顺序、快捷键 | 由各端的本地化、主题和 UX 设置负责；使用 ID 关联 |

内置模式通过 ID 使用各端的语言词条；自定义模式显示定义中的用户名称。颜色由各端主题按 ID 关联，不把终端或桌面端的颜色值写入共享执行定义。

模式 ID 与提示词资产 ID 分别记录。模式 ID 表示用户选择了哪种处理方式；资产的 owner、ID 和 revision 表示这次实际使用了哪份指令。

## 加载与动态注册

候选流程如下，具体文件格式与目录位置尚未确定：

1. 用户创建模式定义，提供稳定 ID、显示名称和对应 prompt。
2. 后端读取定义及 prompt，校验身份、修订、运行选项和引用；同一来源的重复 ID 返回错误。
3. 后端发布新的模式目录版本，并通知客户端重新读取可选模式。
4. 桌面端与 TUI 用目录提供菜单和 `/mode` 选择，不各自维护固定的模式列表。
5. 用户提交时，后端按模式 ID 解析并保存这次实际使用的定义。

定义与 prompt 变更触发重新加载。热更新只改变目录和后续提交可用的定义，正在执行和已经排队的消息保留原定义。加载失败时返回具体诊断，不把该定义发布成可选模式。

本 crate 继续负责内置模式指令资产。模式定义的读取、校验、保存和目录归共享后端的模式领域所有；App Server 提供访问入口。协议定义身份和请求结构，客户端负责选择与显示。实施时按真实调用方确定文件归属，不提前创建模块或接口。

## Prompt、运行选项与权限

五种内置模式已经共用模型调用、工具执行、委托、队列、历史和恢复。自定义模式也使用这套系统；无需把五种模式当成五套执行机制，也不要求每个自定义模式先归入一种内置模式。

普通模式使用定义格式明确规定的普通执行约定：已有 Goal 按现有条件续接，产品命令按已有契约执行，子任务沿用所选模式。需要改变其中某项时，在定义中选择对应的强类型运行选项；后端统一处理，不按名称或 prompt 正文猜测。

| 运行选项 | 候选语义 |
| --- | --- |
| Goal 续接 | 参与已有 Goal 的自动续接，或答完后等待用户 |
| 工作流与 Setup | 按已有契约执行工作流及 Setup Hook，或只交给模型分析 |
| 子任务模式 | 沿用父模式，或明确指定子执行者的模式 ID；创建时保存已解析结果 |

这里是规则语义的候选，不是已经存在的配置字段或协议。模式目录将身份与运行规则分开：模式身份可以扩展，运行选项仍使用后端支持的明确类型。

例如，“故障调查”只需定义 ID、名称和调查 prompt，就可以使用普通执行约定。“代码审查”增加等待用户、仅分析工作流的选项，并在 prompt 中说明不修改项目。“并行整理”在 prompt 中要求委托和整合，并可指定子执行者使用 Agent 模式。

Plan、Ask 当前的不修改要求主要写在 prompt 中；实际动作授权由 Role、目录授权和权限策略控制。自定义模式的 prompt 和运行选项都不能扩大这些授权。若需要工具层强制禁止写入，应由已有权限领域提供明确契约，不能把一句“不修改”当作工具已经被禁止。

普通任务风格和已有规则组合可以通过定义注册。新的执行能力，例如主 Turn 的后台交接，需要在所属运行系统中实现能力与正式接口，再供模式使用；不能只写 prompt 就报告这些操作已经完成。

## 接受、恢复与修改

接受一条消息时，后端解析模式 ID，并保存 ID、定义修订版本、已解析的运行选项和完整指令。持久队列也在接受时保存这些内容，交付时使用已接受的定义。

更改或删除模式只影响后续提交；已经接受的 Turn、排队消息、恢复和重试沿用保存的定义。同一命令的重试仍需检查已接受内容是否一致。新的请求引用不存在或不可用的 ID 时返回明确错误，界面让用户重新选择。

子任务的行为继承继续由后端决定。自定义模式还需要明确哪些附加指令适用于子执行者，避免把协调者要求直接带给每个子任务。

## 采用前需要决定与验证

- 定义的保存范围：用户、项目或共享来源；不同来源的访问、重名和删除规则。
- 定义文件与 prompt 的格式、变更通知、校验诊断，以及目录热更新的发布方式。
- 普通执行约定与可选择运行规则的正式类型；模式身份扩展后，现有代码按模式枚举判断的规则如何统一读取已保存选项。
- 自定义模式附加指令如何继承到子任务，以及协调模式如何指定子执行者的模式。
- 内置名称的本地化、自定义名称的显示、模式颜色和用户排序如何与各端设置结合。
- 模式目录、错误与更新通知的正式协议，以及已有五种模式记录的读取约定。
- 普通发送、排队、跨模式追加、恢复、重试、分支、委托和 Goal 的端到端覆盖。

现有行为约定见 [五种模式](collaboration-modes.md)。只有自定义模式进入明确的产品需求后，才实现本文涉及的目录、保存和协议能力。
