# Agent 时间与等待

时间采样、计时和明确条件的检查由运行时完成；模型只在登记动作及处理结果时参与。本文维护当前等待接口、设计原因、成本边界和与 Codex 的比较。跨 Turn、跨进程的计划归 [automation](automation.md)，扩展装配归 [Agent 扩展](extensions.md)。

## 为什么这样做

- 不让模型为了知道已经等了多久而反复调用读时间工具；相对期限由运行时使用单调时钟计算。
- 不让编译日志或无变化的任务状态反复触发推理；模型可以一次登记“等待命令完成”或“等待子任务满足条件”。
- 保持一个任务的身份：等待同一个命令会话、同一个冻结的子任务集合，不重新启动操作。
- 共用取消、截止时间和事件等待机制；进程状态、Agent 完成条件和日历规则各自由原来的 owner 维护。
- 后台宿主负责运行。关闭某个界面不意味着创建新的模型轮询器；需要跨重启保存的计划使用已有 automation。

Ash 原来的 `ext/clock` 只提供 `sleep`，没有读时间工具。原实现每 5 ms 阻塞检查取消；`wait_agent` 每 25 ms 查询状态，最多 30 秒就返回模型。当前由 `ext/sleep` 暴露计时等待，Agent 等待改为订阅事件，并支持一次明确的长等待。后台命令新增 completion wait，避免每条进度输出都结束工具调用。

## “零 Token”的准确范围

| 阶段                                         | 是否调用模型 | 成本                         |
| -------------------------------------------- | ------------ | ---------------------------- |
| 模型理解任务、登记 Tool Call                 | 是           | 正常输入与输出 Token         |
| 运行时读取时钟、判断截止时间                 | 否           | 本机处理成本                 |
| 等待命令完成、检查子 Agent 状态              | 否           | 事件处理、状态读取、进程资源 |
| 已授权的 CI 监控命令查询外部接口             | 否           | 外部请求配额、网络与进程资源 |
| 条件满足、超时或发生需要处理的错误后继续推理 | 是           | 正常输入与输出 Token         |

“等待期间零模型 Token”不代表整项任务免费，也不代表外部 API 免费。既有异步等待本来就可以不运行模型；本设计额外减少的是反复读时间、短超时和无变化状态造成的模型调用。模型发起动作和最终解释结果仍有成本。

当前时间由显式的 profile 策略控制：`off` 不增加时间上下文，默认 `date` 提供可刷新的日期和时区，`time` 提供秒级时刻。时间语义通过少量输入 Token 表达，不需要读时间 Tool；等待过程仍不调用模型。这里的“按需”由配置明确声明，不使用关键词猜测，也不先调用模型做分类。

文本 Token、本地组装及 sol 对照的历史数据见 [时间上下文实测](benchmarks/time-context-2026-09-13.md)。该对照不是当前生产片段的完整计费量，也不保证所有任务获得相同提速。

同样不承诺“零延迟”：预设等待本身需要时间；计时器、操作系统和网络都有延迟。省掉的是专门读时间和无变化检查所需要的额外模型往返。

## 谁拥有状态

| 位置                                  | 职责                                           | 不承担的工作                     |
| ------------------------------------- | ---------------------------------------------- | -------------------------------- |
| `async-utils` 的可选 `wait` feature   | 异步条件、单调截止时间、取消和通知             | 业务条件、模型调用、持久计划     |
| `ext/sleep`                           | 模型侧计时等待及结构化结果                     | 读取墙上时间、轮询外部服务       |
| `core` 的 Thread owner                | 保存输入参照、组装时间上下文、提交后通知订阅者 | 计算时区规则或伪造用户消息       |
| `agent-environment`                   | 校验并渲染确定的时间快照                       | 读取配置、执行命令、持有生命周期 |
| App Server `ConfigTimeContext`        | profile 策略、系统采样和时区来源               | 改写历史参照或运行等待循环       |
| `ext/agent`                           | 冻结目标，判断 All/Any/Quorum，返回结果        | 每隔固定时间唤醒模型             |
| `tool-executor`                       | 进程生命周期、输出缓冲、完成通知               | 理解日志的自然语言含义           |
| `shell-command` / App Server 工具装配 | 转发带身份和期限的命令等待                     | 第二份进程状态、绕过执行授权     |
| `automation`                          | 持久计划、恢复和到期执行                       | 把当前 Future 保存进数据库       |

crate 用于能力与依赖隔离。纯取消的消费者保持 `async-utils` 默认功能，仅需要等待的消费者启用 `wait`，获得已有依赖中的 `async-io` 计时器和 `event-listener` 通知；没有新建另一个调度服务。

## 时间上下文策略

在 profile 的 `config.toml` 中设置；目录配置不拥有用户的时间解释策略：

```toml
[agent.timeContext]
mode = "date" # off / date / time；默认 date
# timeZone = "Asia/Shanghai" # 省略时使用宿主的 IANA 时区
```

| 策略   | 本次模型输入                                 | 适用条件                                   |
| ------ | -------------------------------------------- | ------------------------------------------ |
| `off`  | 不添加时间尾段和用户时间标签                 | 任务不需要时间语义，避免新增时间 Token     |
| `date` | 当前日期、时区及来源；用户消息带固定日期参照 | 普通对话和同一时区内的相对日期；不提供钟点 |
| `time` | 秒级带 UTC 偏移的当前时刻、IANA 时区及来源   | 需要具体钟点或跨时区判断的任务             |

- `timeZone` 是明确的 IANA 标识，非法值拒绝写入；不把非法或不可用的时区替换成 UTC。
- 配置时区标记为 `configured`；未配置时读取宿主时区并标记为 `host`。宿主可能是远端机器，不能声称它一定是用户所在地；需要用户时区时显式配置。
- 默认 `date` 延续原来的日期环境能力并修复跨日不刷新问题。精确钟点需显式开启 `time`；这不是自然语言需求分类器。
- 配置变更沿既有 Config revision/generation 生效于后续采样，不改变已保存输入的参照。`config/read` 与 `config/update` 的完整字段契约见 [App Server 配置接口](../../docs/ash-app-server-api.md#时间上下文配置)。

### 输入参照和当前快照

1. 宿主把一批文本输入接受进 Thread 历史时，采样并保存 `TimeContext`，包括时间戳、时区、当时的 UTC 偏移、来源和精度。初始输入和执行中的追加输入都走此入口；它不是用户设备发送时间。
2. 原始 `UserMessage.text` 保持原文，时间参照存放在历史 envelope 元数据中。命令重试返回原接受结果，不重新采样或改写已接受的输入。
3. 每次重新准备模型请求时，重新读取 profile 策略并采样当前时间；用户输入的参照从历史读取，不能拿本次时间重新解释过去的“昨天”。
4. Core 在请求副本中给用户消息加 `user_time` 标签，在稳定历史之后加 `time_context` 尾段。标签与尾段参与预算计算；不会另造用户消息或修改持久正文。
5. 工具返回、等待恢复和上下文重新规划后得到新快照。同一逻辑请求的传输/暂时性失败重试复用已冻结的请求快照，标签明确表示“请求准备时采样”，不承诺生成期间时钟持续更新。
6. 完成的模型调用在 `ModelInvocationRecord.timeContext` 中记录实际使用的快照，便于审计；源输入参照由 history schema 18 保存，恢复及保留历史的分支都沿用原值；渲染历史时使用保存的偏移，不用新版时区规则重新计算。

例如输入在洛杉矶 `2026-09-12 23:59:50` 被接受，内容为“昨天的日志”；工具完成时已经是 `2026-09-13 00:00:05`。模型会同时看到原消息日期 `2026-09-12` 与当前日期 `2026-09-13`，“昨天”仍对应 `2026-09-11`。

启用时间上下文时，自动压缩、手动压缩及溢出恢复的源材料也包含原消息的时间参照；压缩过程本身不另加当前时间。

旧历史或在 `off` 下接受的消息没有参照，开启时间上下文后明确标记 `user_time unavailable`，不补写今天或猜测当时的时区。切换 `date` / `time` 不改变旧消息已记录的精度；`off` 关闭所有派生时间标签。配置策略变化可能使请求前缀变化一次，日常当前时间刷新只改变请求尾段。

App Server capability version 5 与 history schema 18 标识这组行为，客户端和后端需要同步升级。旧历史可读，但不存在的输入参照保持未知。

`current_date` 已从连接级 `HostEnvironment` 退场，连接建立不再通过 `date` 命令采样日期。平台、Shell 和仓库摘要继续作为连接快照；时间使用独立的请求生命周期。

## 当前工具接口

### 计时等待 `sleep`

```json
{"duration_ms": 10000}
```

- `duration_ms` 必填，整数，范围 `0..=43200000`，最多 12 小时；`0` 立即完成。
- 不接受其他参数，也不通过 shell 启动计时进程。
- 完成返回 `{"reason":"elapsed","elapsed_ms":...}`；耗时由单调时钟计算。
- 取消停止等待，不发布成功完成项。到期发布扩展身份 `sleep` 的结构化等待项；现有 `content.type = sleep` 表示计时结果，其毫秒值上限同步为 12 小时。
- `ext/clock` 已退场，模型侧纯计时工具保留 `sleep` 名称。Code Mode 的 `wait` 已用于执行单元，不与计时工具混用；各入口共用等待机制，保持各自的任务条件与结果。已有历史项继续作为历史数据读取。
- 此调用属于当前执行；不会在进程重启后自动延续计时或安排新 Turn。

### 子任务等待 `wait_agent`

- 既有 `delegation_id` / `delegation_ids`、`policy`、`quorum` 继续表达一个、多个或全部当前子任务及 All/Any/Quorum 条件。
- 第一次建立 join 时冻结目标集合；后来启动的子任务不会悄悄加入本次等待。
- `timeout_ms` 为 `null` 或省略时使用 12 小时；`0` 返回当前 join 状态；超过 `43200000` 明确拒绝，不静默截断。
- 先订阅父任务和选中子任务的提交事件，再读取状态。已完成的子任务在注册前后完成都能被观察到。
- 中间事件只让运行时重查条件；条件未满足时不返回模型。子任务出现审批或用户输入请求时提前返回 `reason: needs_input` 和请求身份，让用户处理；不靠重复调用等待工具解决。
- 满足条件返回 `satisfied` 和结果；截止时返回持久化的 `waiting` join，不取消子任务。
- Turn 取消传播给等待；join 的持久事实不等同于一个可跨重启继续运行的内存 Future。

### 命令等待 `shell-session`

该工具保持一个进程会话。新增 `action: "wait"`，其余身份、输出游标和操作沿用原工具。

| 参数或操作                        | 当前语义                                            |
| --------------------------------- | --------------------------------------------------- |
| `start` 的 `timeout_ms`           | 命令运行期限；默认 30000，范围 `1..=43200000`       |
| `start` / `read` 的 `wait_ms`     | 本次等输出多久；默认 0，最多 30000                  |
| `wait` 的 `wait_ms`               | 本次等完成多久；默认 43200000，范围 `0..=43200000`  |
| `wait` 的 `session_id`            | 必填的既有命令身份，校验所属 Session、Thread 和环境 |
| `stdout_cursor` / `stderr_cursor` | 独立游标；默认 0；沿用输出截断和 gap 语义           |
| `read`                            | 等待并读取新增输出，适合交互或查看进度              |
| `wait`                            | 等待最终状态；中间输出留在有界缓冲，不结束本次等待  |
| `interrupt` / `terminate`         | 显式中断或终止已有进程                              |

`wait` 返回既有命令状态及输出；`running` 表示本次期限已到、命令仍在运行。命令自身运行期限到达会返回 `timed_out`，两种期限不能混为一谈。取消观察本身不调用终止进程；如果同一 Turn 同时拥有该进程，Turn 取消仍按进程 owner 的既有生命周期规则终止它。

等待不能延长或重置进程运行期限；长编译或 CI 监控必须在 `start` 时明确提供适当的 `timeout_ms`。所有启动仍经过既有目录、网络、沙箱与审批流程。监控一个外部 CI 的本地进程退出，不表示远端 CI 已被取消。

### 编译与 CI 如何接入

1. 使用 `shell-session start` 启动一次已授权的编译或 CI 监控命令，并设置命令运行期限。
2. 若已结束，直接处理结果；若返回命令身份，使用一次 `shell-session wait` 等待最终状态。
3. 编译日志或监控命令的内部 API 查询均不进入模型循环。
4. 运行成功、失败、达到期限或被取消后，由既有工具结果路径继续处理。

CI 监控需要已安装且已认证的命令或服务适配；选择确定的任务身份，监控命令应在任务结束时退出并用退出状态区分成功与失败。当前未新增通用 Webhook 接收器，也未增加能任意访问 URL、凭据或重试有副作用操作的通用轮询工具。需要语义判断的条件仍交给模型。

## 竞态、取消与恢复

- 使用 `Instant` / `Duration` 表达运行期间期限；墙上时间校正不改变等待预算。持久日历调度的时间规则见 [automation](automation.md#时间分别如何表达)。
- 通知只表达“需要重查”；数据仍由 Thread journal 或进程状态保存。调用方必须先订阅再检查，避免丢失发生在检查与挂起之间的完成事件。
- 每次 poll 先检查取消，再检查条件，再检查截止时间；已经可读的完成结果优先于同时到达的观察截止时间。
- Future 被释放时撤销通知和计时注册；没有每个等待单独创建一个计时线程。
- Thread 提交后的通知不新增历史消息，不调用模型。恢复时重新读取持久事实，不能把旧通知当作新的工作请求。
- 普通计时等待和命令进程不跨重启存活；需要未来执行的工作提交给 automation。自动化到期启动 Agent 后，模型仍然正常计费。

## 优势、代价与限制

| 方面       | 优势                                              | 代价或限制                                                      |
| ---------- | ------------------------------------------------- | --------------------------------------------------------------- |
| Token      | 无变化状态不要求再次推理                          | 首次动作、结果分析和明确超时后的恢复仍有 Token                  |
| 延迟       | 完成事件可直接唤醒运行时                          | 系统调度、进程监督和外部轮询仍有延迟                            |
| 取消       | 共用取消令牌与截止语义                            | 必须区分观察取消、进程取消和远端任务取消                        |
| 资源       | 计时和条件 Future 挂起，无固定频率 Agent 状态查询 | 现有同步 ToolService 入口仍会停驻执行线程；进程仍有 IO/监督线程 |
| 灵活性     | 明确条件稳定、可验证                              | “结果是否值得关注”等开放问题仍需要模型                          |
| 故障处理   | 明确失败和截止后交回结果                          | 监控接口、授权失效和网络错误由具体适配处理                      |
| 持久性     | 复用现有 automation，避免第二套计划存储           | 当前 Turn 的等待不自动升级为持久任务                            |
| 进度可见性 | 中间日志不反复进入模型上下文                      | 等完成期间模型不会逐段分析日志；需要时显式使用 read             |

进程监督内部仍可能进行本机状态检查；CI 监控命令也可能轮询 API。这些都不调用模型，但仍有 CPU、网络、配额和限流成本。不能用“零 Token”替代这些资源的预算。

## 与 Codex 的源码比较

比较基于本机 `../codex`，提交 `a592c38c16cdd7623dacc9168926ebccedfb67d3`。这是该源码版本的行为核对，不代表全部发行版本或线上配置。

| 能力             | 该版本 Codex                                             | 当前 Ash                                               |
| ---------------- | -------------------------------------------------------- | ------------------------------------------------------ |
| 模型读时间       | 可暴露 `clock.curr_time`；另有按请求边界及间隔注入的提醒 | 无读时间工具；按 off/date/time 策略提供请求快照        |
| 用户相对日期参照 | 本对照未审计所有输入时间语义                             | 每条文本输入保存时区与参照，恢复及历史分支保持原值     |
| 等待本身的 Token | 异步等待期间无需推理                                     | 同样无需推理；主要节省反复检查导致的模型调用           |
| 计时等待         | `clock.sleep`，异步计时，可被输入活动打断                | `sleep`，共享取消与截止机制；观察 Turn 取消            |
| Agent 等待       | V2 等待邮箱、输入或超时；与 sleep 共用输入活动订阅       | 按冻结集合判断 All/Any/Quorum；提交事件驱动条件重查    |
| 命令输出         | 专门管理输出、退出、取消与等待期限                       | read 返回进度；wait 只返回最终状态或期限结果           |
| 长期调度         | 不能从 sleep 推导持久恢复能力                            | 由已有 automation 单独负责，不把 wait 当持久计划       |
| 运行时形态       | 所核对的等待实现使用 Tokio 异步机制                      | 共享等待 Future 不要求 Tokio；同步工具宿主仍有停驻线程 |

核对入口：Codex 的 `core/src/session/time_reminder.rs`、`core/src/session/turn.rs`、`core/src/current_time.rs`、`core/src/tools/handlers/sleep.rs`、`core/src/tools/handlers/multi_agents_v2/wait.rs` 及 `core/src/unified_exec/process_manager.rs`，均位于 `codex-rs/` 下。

不能声称 Codex 的 sleep “占用线程死等”，也不能声称只有 Ash 能在等待期间不消耗 Token。Ash 此次改进针对的是自己原有的固定间隔查询、短期限返回模型及命令进度返回行为。

## 维护与验证

- 修改等待条件时，同步其 owner、工具描述、本文和真实调用链测试。
- 新增外部适配时，必须说明任务身份、可判定的完成条件、截止、取消、鉴权、限流和失败处理；不能默认重试有副作用动作。
