# 时间上下文核对与实测（2026-09-13）

> 本文保留时间上下文实现之前的核对与基准结果。当前已接入的策略与生命周期见 [Agent 时间与等待](../agent-wait.md)；下文“尚未实现”描述的是测量当时的状态。

在这组 sol 小样本对照中，直接使用时间上下文比先调用读时间工具少一次模型往返，模型阶段的配对耗时差中位数为 **1.974 秒**。这支持在确有时间语义需求时减少独立读时调用；不能承诺所有任务固定快 1～3 秒。当前 Ash 尚未实现按需注入最新时间快照，本文不改变生产行为。

## 已确认的实现事实

| 问题 | 核对结果 | 依据 |
| --- | --- | --- |
| 当前日期何时采样 | 环境连接建立时执行 `date +%Y-%m-%d` | [AgentEnvironmentSource](../../app-server/src/server/agent_environment_source.rs) |
| 后续推理是否刷新 | 复用原 host 快照；不会刷新日期 | 同文件 `snapshot` 与 [环境渲染](../../agent-environment/src/render/environment_context.rs) |
| 是否已有时区字段 | HostEnvironment 没有时区字段 | [HostEnvironment](../../agent-environment/src/model/snapshot.rs) |
| 本次等待改造是否已经包含动态时间注入 | 没有；等待由运行时处理，未新增逐请求精确时间戳 | [Agent 时间与等待](../agent-wait.md) |
| 时间片段能否放在可复用前缀之后 | Core 已有请求尾部环境位置和显式前缀边界；本地基准验证了此前缀不变 | [ContextAssembler](../../core/src/context/assembler.rs)、[基准](../../core/src/context/benchmarks.rs) |
| 能否直接用 Ash 当前模型测在线延迟 | 检查时默认模型与供应商配置为空；用户改为明确选择 Codex sol 子 Agent | 不复制本机用户配置或凭据到报告 |

### 三种时间不能混用

- 运行耗时与超时由运行时的单调时钟计算，不要求模型读取当前年月日。
- 模型解释用户的相对日期时，需要明确参照时刻和时区；可由运行时先解析成确定范围。
- 每次请求新采样的“现在”不能改变已经解释好的用户意图。例如用户在 `2026-09-12T23:59:50-07:00` 请求“昨天的日志”，其日期为 **2026-09-11**；若执行跨午夜后按 `2026-09-13T00:00:05-07:00` 重新计算，会错误地改为 **2026-09-12**。日期计算已用 Python 标准库核对，未把它当成模型质量测试。

“每天 17 点”可以交给日历调度器；产物时间戳可以由生成脚本填写。文档发布年份较早本身不能证明内容失效。只有具体消费者需要模型结合时间作判断时，才能据此要求给模型提供时间信息。

## 文本 Token 计数

使用 Python 3.12.12、`tiktoken==0.12.0`，对同一组文本分别运行两个公开 encoding。**没有将它们冒充 sol 的准确 tokenizer，也没有计算供应商消息封装或计费 Token。** 所有编码都验证了 decode 后与原文一致。

| 文本 | cl100k_base | o200k_base |
| --- | ---: | ---: |
| `2026-09-12` | 6 | 6 |
| `2026-09-12T19:29:47-07:00` | 16 | 16 |
| `当前时间：2026-09-12 19:29:47` | 15 | 15 |
| 完整时间戳加 `<current_time>` 标签 | 24 | 24 |
| 时间戳、IANA 时区和 `<time_context>` 标签 | 37 | 36 |
| 用户请求参照时间、当前采样时间、时区及标签 | 61 | 60 |

因此，“只需约 10 Token”不能作为通用上限。短片段通常是几十个文本 Token，精度、时区和参照信息都会改变大小；实际输入计费仍以指定模型的 usage 为准。

- [固定文本、token ID 与计数](time-context-tokens-2026-09-13.json)
- [可复现计数脚本](../../model-tokenizer/benchmarks/time_context.py)

```sh
python3.12 -m venv .build/time-context-python
.build/time-context-python/bin/python -m pip install tiktoken==0.12.0
.build/time-context-python/bin/python ash-rs/model-tokenizer/benchmarks/time_context.py \
```

## sol 在线对照

用户明确选择 sol 子 Agent 后，通过当前 Codex 账号完成测试，未使用本地 Ash 模型配置，也未读取或导出账号凭据。

| 条件 | 实际设置 |
| --- | --- |
| 模型 / 推理强度 | `gpt-5.6-sol` / `low`，从每个子任务记录确认 |
| A 路径 | 提供时间快照；直接输出该 UTC 时间；不调用工具 |
| B 路径 | 强制一次 `functions.exec` 调用 `clock.curr_time`；再输出同格式 UTC 时间 |
| 输出限制 | 单行 `YYYY-MM-DD HH:MM:SS UTC`，不解释、不读文件、不浏览 |
| 历史 | 每个样本新建无父会话历史的子 Agent，保留 Codex 宿主的共同指令与工具定义 |
| 样本数 | 2 对预热/试运行，6 对正式样本；原始数据包含全部 16 个任务 |
| 顺序 | 正式样本交替采用 A→B、B→A；没有随机化；实际执行区间不重叠 |
| 缓存 | 正式样本 A 均报告 32512 cached input；B 两次推理合计均为 65024 |
| 时间口径 | 子任务自身事件时间戳；不使用父 Agent 读到结果的时刻 |

### 如何计时

- **模型阶段**：该子任务 `turn_context` 记录到 `final_answer` 记录；涵盖模型请求准备之后的网络、排队、生成及工具往返，不是单独的服务器推理时间，也不是直接 API 的 TTFT。
- **子任务总耗时**：`task_started` 到 `task_complete`；包含子 Agent 初始化和准备工作，不包含父 Agent 生成派发工具调用的时间。
- **工具包装调用**：`functions.exec` 调用记录到对应结果记录；包含包装和宿主通信，不能当成单独读取系统时钟的 CPU 耗时。
- **工具返回后恢复**：工具结果记录到最终回答，包含后续模型请求和生成。
- 时间来自毫秒级墙上时钟日志；本轮未发现时间倒退。机器不是独占测试环境，采样期间主任务也执行了本地编译校验。

### 每对差值

正数表示 A 更快。配对差中位数与“两个独立中位数相减”不是同一个统计量。

| 对次 | A 模型阶段 | B 模型阶段 | 模型阶段 B−A | 子任务总耗时 B−A |
| ---: | ---: | ---: | ---: | ---: |
| 3 | 1.720 s | 3.093 s | 1.373 s | 1.355 s |
| 4 | 1.672 s | 3.329 s | 1.657 s | 1.367 s |
| 5 | 1.370 s | 3.726 s | 2.356 s | 1.851 s |
| 6 | 1.499 s | 3.790 s | 2.291 s | 2.777 s |
| 7 | 2.181 s | 3.126 s | 0.945 s | **−0.466 s** |
| 8 | 1.424 s | 4.900 s | 3.476 s | 2.945 s |

模型阶段配对差中位数 **1.974 s**，范围 **0.945–3.476 s**；子任务总耗时配对差中位数 **1.609 s**。第 7 对受初始化等因素影响，A 的子任务总耗时反而更长。数据支持少一次独立读时往返，但不支持每次整项任务固定节省 1～3 秒。

### 实际 usage

正式样本在每条路径上的以下计数一致，来自 Codex 返回的 usage，而非本地估算。

| 整条路径的累计 Token | A | B |
| --- | ---: | ---: |
| 输入 Token | 32908 | 65860 |
| 其中 cached input | 32512 | 65024 |
| 未报告为 cached/cache-write 的输入 | 396 | 836 |
| 输出 Token | 17 | 43 |
| 推理输出 Token | 0 | 0 |

B 多出一次约 3.3 万输入 Token 的模型请求，但大部分命中缓存；额外输出为 26 Token。共同宿主指令和工具定义占了输入的大部分，不能把这些 Token 都归给时间片段。A/B 的操作指令也不同，不能用两者第一轮输入差推算时间戳的精确 Token 数。

本实验在 Codex 账号内运行，没有据此套用 API 单价或推算金额。缓存 Token 仍是 Token，费用和配额如何计算属于具体服务的计费规则。

### 适用范围

- B 被要求单独读时间；实验没有证明普通任务都会自然发起该调用。
- 当前 Codex 宿主可能也带有日期等环境信息；这里强制区分“使用给定快照”和“调用读时工具”，不是移除全部宿主时间提示的裸 API 对照。
- A 验证的是遵循输入快照，B 验证的是读取工具后作答；不把两条路径输出的现实时间值相等作为判据，也不评估业务日期解析质量。
- B 使用了当前可用的代码包装工具；不同工具接口、模型、推理强度、上下文长度、冷缓存和服务负载需重新测量。
- 若读时间与其他必要工具合并在同一轮，后续模型请求本来就会发生，不能把这里的整轮收益直接套用。

## 工程决定与未完成项

- 保持运行时负责计时、等待和明确条件判断；这些行为无需新增模型调用。
- 在确实需要时间语义、且能够替代独立读时往返的路径上，短时间片段有实测支持。
- 尚未实现时间需求的触发协议、用户时区来源、参照时刻冻结和请求级新鲜度保证；不能仅写“按需注入”就声称工作已完成。
- 不为判断是否需要时间而单独调用一次大模型。结构化任务应由明确字段声明需要的时间信息；自由对话的默认策略仍需单独设计与行为测试。
- 若实现请求级时间片段，保留稳定前缀，在请求审计中记录实际采样值，不持续向对话历史追加时钟消息。
- 日期刷新与时间语义质量应单独验证跨日、时区和恢复场景，不能用延迟基准代替。

官方文档同样建议减少串行请求，并把动态内容放在可复用前缀之后；实际缓存效果还取决于模型与缓存边界配置，应查看实际 usage。[延迟优化](https://developers.openai.com/api/docs/guides/latency-optimization#make-fewer-requests)、[提示缓存](https://developers.openai.com/api/docs/guides/prompt-caching#monitor-cache-performance)。这些通用建议不提供本任务固定的秒数或价格承诺。

本轮验证：离线 Token 编码往返校验、Core 基准断言、包级编译与 warning gate、Python 格式与静态检查通过。没有修改生产时间注入或模型选择配置。
