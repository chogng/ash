# 输入状态的归属与复用

Ash 复用输入控件和编辑能力，输入内容由对应功能按业务身份管理。
两个入口是否共享内容，取决于它们是否编辑同一份数据，不能由控件相同、
页面相邻或挂在同一个 Workbench 下决定。每份可变状态只能有一个拥有者。

本文适用于 `src` 的各类输入，包括 Chat、Code、SCM、搜索、表单、
快捷输入、文件编辑和终端输入。前半部分规定新增和修改输入时的归属规则；
后半部分记录 Sessions 的当前实现。场景表中的要求不代表这些功能均已实现。

## 按状态的用途确定拥有者

“输入状态”不只是文本，也包括未提交选项、附件、校验结果和提交过程。
这些状态的寿命不同，不应全部塞进控件或窗口服务。

| 状态                                       | 拥有者                                             | 共享边界                                                 |
| ------------------------------------------ | -------------------------------------------------- | -------------------------------------------------------- |
| 焦点、光标、选区、输入法组合、浮层         | 控件或编辑视图                                     | 随视图管理，另一个入口不能接管正在进行的交互             |
| 未提交文字、附件、表单字段、局部选项       | 该功能的草稿拥有者；仅随控件存活时可由控件直接持有 | 独立输入分别保存；只有业务明确要求共同编辑时才共享草稿   |
| 文本模型、撤销记录、修改标记               | 该份文本的编辑模型                                 | 独立草稿使用独立模型；同一文件的多个视图可以使用同一模型 |
| 字段校验、搜索结果、补全候选               | 对应功能的模型或操作                               | 对应产生结果的输入身份和值，不能把旧结果应用到新输入     |
| 提交快照、请求状态、取消和错误             | 发起操作的功能对象                                 | 绑定原始目标和本次操作，不能跟随当前焦点或页面选择变化   |
| 已发送消息、已保存配置、文件内容、提交结果 | 对应业务服务或资源模型                             | 按业务身份共享；显示同一份结果不等于共用未提交输入       |
| 新输入的默认选项、历史候选                 | 对应配置或历史服务                                 | 可在明确范围内共用；不能用默认值覆盖已有草稿             |
| 当前页面、选中对象、面板集合、导航         | 所在功能的视图协调者                               | 决定显示哪份输入，不成为输入内容的第二个拥有者           |

控件展示业务模型时，值的修改必须回到同一个模型；不得让 DOM 值、控件缓存
和服务各自维护一份权威内容。需要跨控件重建保留的草稿，由功能持有；
只在一次对话框调用中有效的值，可以随该调用释放。是否使用文本编辑器、
`InputBox` 或 `textarea`，不改变这条规则。

Workbench Part 负责容器与显示。基础控件负责通用编辑、键盘与无障碍行为；
功能负责内容、校验、提交和恢复。遵守 `base → platform → editor → workbench`
的依赖方向，不能为了复用输入框把会话、仓库或业务草稿放进 `base`。
`ChatInputPart` 保留 Chat 语义，不作为所有输入的统一入口，也不建立保存
全窗口当前输入的全局对象。组件样式边界见
[Renderer UI 样式所有权规范](ui-styling-ownership.md)。

## 输入身份与共享范围

新增输入时，先说明它属于哪个功能、编辑哪个对象、承担哪种输入用途，
以及是否需要跨页面、窗口或重启保留。身份由功能定义，不由 DOM 位置、
当前选中对象、显示标题或组件类名推断。

| 身份要素                     | 何时需要                                 | 示例                               |
| ---------------------------- | ---------------------------------------- | ---------------------------------- |
| 功能与入口                   | 不同功能需要独立草稿                     | Chat 消息与 SCM 提交说明           |
| 业务对象或资源               | 同功能可以同时编辑多个对象               | Thread、仓库、文件 URI、待编辑记录 |
| 输入用途或字段               | 同对象有多个不同输入                     | 搜索词与替换词、记录标题与正文     |
| 草稿或调用身份               | 尚未有正式对象，或同对象允许多份独立草稿 | 多个未创建会话、两次对话框调用     |
| 工作区、用户配置档、远端范围 | 数据或恢复规则随这些范围变化             | 工作区查询、用户设置、远端仓库     |
| 视图或窗口身份               | 产品要求同对象在不同视图有独立草稿       | 两个窗口各自编写未发送消息         |

这些是选择身份的依据，不要求所有输入都拼接同一套字段。创建草稿时确定
身份；未创建对象取得正式身份时，由拥有者维护对应关系。不能用新的“当前
对象”替换仍在读取附件或提交的输入目标。

需要共享时，明确采用哪一种行为：

| 行为             | 状态关系                     | 约定                                                 |
| ---------------- | ---------------------------- | ---------------------------------------------------- |
| 共用控件实现     | 各自创建实例和草稿           | 修改一处不会改变另一处内容                           |
| 显示同一业务对象 | 共用已保存数据，草稿仍可独立 | 同 Thread 历史共用；不同窗口可以保留各自草稿         |
| 共同编辑         | 多个视图绑定同一个业务模型   | 例如同一文件分屏；明确内容、撤销、保存与关闭的关系   |
| 内容交接         | 将一次内容交给明确目标       | 说明复制还是移动、目标有草稿时如何处理、何时清理来源 |

共同编辑只由业务契约启用；同名存储键或意外复用实例不能成为共享方式。
交接完成后的两份独立草稿各自演进。共享模型和订阅的释放由拥有者管理，
关闭一个视图不能释放其他视图仍在使用的资源。

## 不同输入的归属示例

下表用于确定设计边界。具体恢复范围与交互规则由各功能补充，不能直接
照搬 Sessions 的草稿存储或发送流程。

| 场景                                | 输入归属                     | 应保留的区别                                                   |
| ----------------------------------- | ---------------------------- | -------------------------------------------------------------- |
| Sessions Chat / Code 消息输入       | 窗口中具体会话面板的草稿     | 切换布局保留同一输入；不同会话的文字、附件与发送选项独立       |
| SCM 提交说明                        | SCM 的仓库输入模型           | 切仓库不能带走另一仓库的说明；提交绑定原仓库                   |
| 工作区搜索与替换                    | 搜索功能的一次查询状态       | 搜索词、替换词、范围和选项各有用途；共享查询应明确启用         |
| 列表筛选、编辑器内查找              | 对应列表或编辑视图的查询状态 | 不与工作区搜索或其他列表使用一份“当前搜索文字”                 |
| Quick Input、命令参数、重命名对话框 | 一次调用及其目标对象         | 连续调用有独立身份；历史候选与当前值分别管理                   |
| 设置输入                            | 设置页的编辑状态与配置服务   | 尚未通过校验的文本不是已保存配置；搜索框也不是配置值           |
| 业务表单                            | 具体记录的表单模型           | 多字段组成一份草稿，共同校验和提交；切记录有明确保留或放弃规则 |
| 文件编辑                            | 文件资源模型与编辑视图       | 相同资源可共享内容，各视图保留自己的选区和滚动位置             |
| 终端输入                            | 具体终端实例与其进程         | 按键经终端送入进程；历史候选与正在输入的命令分别管理           |
| 后续新增的输入                      | 所属功能按对象和用途定义     | 使用已有控件，先确定身份、状态寿命与提交目标                   |

[Preferences 与 Settings 的职责](preferences-and-settings.md)说明设置页面、
JSON 编辑和快捷键编辑如何共享对应数据，并分别管理页面与输入。

## 生命周期与异步操作

输入寿命按业务规则确定，不能仅靠 DOM 是否可见判断。

| 变化           | 必须明确的行为                                                       |
| -------------- | -------------------------------------------------------------------- |
| 隐藏或切页面   | 是否保留原输入；隐藏不等于提交、清空或把草稿交给新页面               |
| 切换业务对象   | 原草稿保留、提交或放弃的规则；新对象读取自己的状态                   |
| 控件重建       | 恢复同一输入还是新建输入；释放旧监听、模型引用和局部异步任务         |
| 关闭视图       | 处理未提交内容并释放视图资源；共享业务模型是否继续存活由其拥有者决定 |
| 提交成功或失败 | 成功清理哪份内容，失败保留什么，错误在哪个输入显示                   |
| 窗口退出与重启 | 哪些草稿写入存储、写入何时完成，以及下次恢复哪些输入                 |

发起附件读取、校验、搜索或提交时，记录原输入身份和本次操作所需的值。
回调通过发起者处理结果，不能重新查询“当前输入”决定落点。值已经改变时，
旧校验和搜索结果不能覆盖新结果；提交期间允许继续编辑时，成功只清理
已提交的内容，不能删掉之后新增的文字或附件。具体功能可以用模型版本或
操作身份实现这一约定，不要求所有输入共用一个异步状态机。

视图销毁时停止由它拥有的局部任务。已发出的业务操作是否取消，由业务服务
和操作契约决定；不能因切页面重新提交，也不能让已销毁控件继续更新界面。

## 保存与恢复规则

持久化由功能显式选择。临时对话框不必保存草稿；需要恢复的编辑内容不能
因为复用同一个控件就共用存储键。写入方和恢复方遵守同一份功能契约：

| 要确定的内容   | 要回答的问题                                                               |
| -------------- | -------------------------------------------------------------------------- |
| 保存对象与字段 | 保存当前草稿、历史候选还是用户默认值？哪些字段允许恢复？                   |
| 范围与身份     | 属于哪个工作区或用户配置档？如何区分功能、对象、用途和独立草稿？           |
| 恢复时机       | 新实例首次创建、对象再次打开还是窗口启动时恢复？新建输入是否从空内容开始？ |
| 多份草稿       | 全部恢复还是只恢复最近一份？运行期间隔离是否也能跨重启保持？               |
| 多窗口         | 窗口间独立、共同编辑还是显式交接？并发写入如何避免相互覆盖？               |
| 清理与身份变化 | 提交、取消、对象删除或未创建身份转正式身份时，哪些键更新或移除？           |

不能把独立草稿写进同一个键，再声称输入已经隔离。运行期间、跨重启、
跨窗口是三个不同范围，分别说明实际保证。保存草稿也不自动表示会恢复
当前选择、布局或导航。配置值的归属继续由配置服务负责，不存进草稿代替配置。

## Sessions 当前实现：调用与生命周期

Sessions 窗口只有一份当前会话、可见会话和前进后退记录。
Chat、Code 和协作入口调整周围面板，保留相同的会话与输入实例。
Library、Design 通过 `IEditorService` 打开，暂时隐藏会话面板。

`ISessionsManagementService` 管理会话目录、未创建会话的身份和后端操作。
`ISessionsService` 管理窗口的选择、可见集合和导航；目录更新不会自行
切换前台会话。`SessionsPart` 保留一个 `SessionsChatView`，每个可见会话
各自创建 `ChatWidget`、`ChatWidgetModel` 和 `NewChatInputWidget`。
文字、附件和本次输入操作由输入实例管理；模式、模型、思考强度与权限选择
由该面板的 `ChatWidgetModel` 管理。

新建、选择、关闭和前进后退作用于窗口的共同选择。关闭已创建会话的面板
不会归档后端会话；关闭未创建会话会清理其身份和草稿。
首次发送将未创建身份对应到正式 Session / Thread。管理服务保留对应关系，
窗口服务更新面板与导航。发送过程中切换布局或新建会话，完成结果仍属于
原来的输入，不能自动占据前台。

不同使用者明确打开同一个 Thread 时，`ChatService` 按使用者保留订阅。
最后一个使用者释放后才取消后端订阅。Chat / Code 切换保留同一个使用者。
普通 Workbench 的交接进入窗口的共同会话选择，原有独立会话草稿仍可在
会话列表中重新打开。面板、输入实例和事件监听随窗口释放。

## Sessions 当前实现：草稿存储

草稿使用工作区范围，按具体会话身份保存：

| 输入身份      | 存储键                                             |
| ------------- | -------------------------------------------------- |
| 未创建会话    | `sessions.inputDraft:untitled:<untitledSessionId>` |
| 已创建 Thread | `sessions.inputDraft:<threadId>`                   |

`sessions.viewState` 保存全部未创建身份、可见集合及当前选择。
`sessions.gridState` 保存共同分屏宽度。重启恢复这些身份及各自草稿，
导航记录从恢复的当前选择开始，不跨重启保存完整历史。

旧的 Chat / Code 选择合并为一个可见集合。同身份的相同草稿合并；
同身份的不同内容和旧的页面级草稿另建未创建会话，写入新键后才移除旧键。
首次发送成功会转移并清理对应未创建草稿，后续按 Thread 保存。
窗口关闭时等待附件读取和草稿写入，再刷新存储。

## 与 VS Code 的关系及实现范围

本设计沿用其职责划分：复用编辑能力，按功能和实例管理文本状态。
本地 VS Code 源码中，Workbench Chat 的 `ChatInputPart` 创建实例自己的
输入模型；Sessions 的 `NewChatInputWidget` 拥有自己的编辑器与文本模型；
SCM 的 `SCMInputWidget` 使用仓库提供的 `inputBoxTextModel`。
这是按具体功能、模型和实例确定归属，而非把全部输入划成
“Sessions 输入框”和“Workbench 输入框”两个全局对象。

Ash 的 SCM 目前仍在 `workbench/contrib/scm/browser/scmViewPane.ts` 中使用
`textarea`。本文要求其业务状态按仓库管理，不表示 SCM 已完成模型改造。
搜索、表单等示例同样是归属规则，具体实现需要在各自功能内核对。

## 新增输入与验证

新增或修改输入时，在所属功能的接口注释或行为文档说明以下事项；
本文维护共通规则，不登记所有输入实例，也不要求为每个输入新建文档。

1. 明确用途、业务目标和输入身份，以及每种状态的唯一拥有者。
2. 决定控件复用、数据共享、共同编辑或内容交接，写清目标已有内容时的行为。
3. 明确隐藏、切对象、关闭、重建和异步完成时的行为。
4. 需要保存时，说明字段、存储范围、多份草稿、多窗口和清理规则。
5. 使用所属层已有控件与模型，只为实际消费者补充共通能力。

验证按该功能真实存在的行为选择：独立输入互不影响，同对象多视图符合共享
约定，切对象后旧回调不写错目标，提交不清掉新编辑，关闭一个视图不破坏
其他使用者，保存和恢复符合声明范围。模型与操作用对应测试验证；界面行为
通过 Playwright 检查值、焦点和目标，在受影响的浏览器或 Electron 项目运行。

### Sessions 的修改入口与已有覆盖

会话选择和导航改在 `services/sessions/browser/sessionsService.ts`；
会话身份变更改在 `services/sessions/browser/sessionsManagementService.ts`；
输入操作、文件读取和存储策略改在 `contrib/chat/`。
基础编辑能力和共用 Chat 操作留在 `editor/` 与 `workbench/contrib/chat/`。

`sessions-view-service.test.ts` 验证共同选择、导航、关闭、旧数据合并和后台首次发送；
`sessions-part.test.ts` 验证布局切换时实例保留及会话之间的草稿、附件隔离；
`chatViewPane.test.ts` 验证真实聊天模型的首次发送和订阅释放。
Playwright 的 Sessions 场景验证布局切换、刷新、输入与附件，
分别运行浏览器、Electron UI 和连接 App Server 的 Electron 项目。
