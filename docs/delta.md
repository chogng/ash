# Delta 能力与体验指南

Delta 是让人和 Agent 围绕同一项代码工作持续协作的工作空间。它把讨论、文件变化和审查放在同一个线程里，让参与者能接着原来的工作继续，而不是重新解释代码产生的过程。[官方介绍](https://delta.dev/)

本文帮助读者理解和体验 Delta，内容以 Delta 自身的能力为准。Ash 的功能建设方案另行讨论。

## 先理解一项工作怎样放在一起

| 概念 | 在 Delta 中的含义 |
| --- | --- |
| Thread，线程 | 一段与 Agent 的持续对话，可以关联零个、一个或多个项目 |
| Project，项目 | 加入线程的 Git 仓库根目录 |
| Delta worktree | 某个项目的文件与变化历史，由 DeltaDB 记录并在参与者之间同步 |
| Checkout，工作副本 | 桌面机器上的实际文件目录，供终端、构建工具和其他程序使用 |

一个线程通常为每个项目持有独立的 Delta worktree。桌面上的 checkout 与它同步；Delta 管理的工作副本并非用 Git 的 `git worktree` 实现。用户也可以选用已有本地目录，此时使用该目录的线程会共享文件修改。[核心概念](https://delta.dev/docs/concepts/core-concepts)、[工作副本说明](https://delta.dev/docs/concepts/worktrees)

例如修复一个按钮问题：在线程里讨论方案，Agent 修改对应文件，你针对方案或代码留下意见，再继续修订。下次打开原线程时，讨论和未提交的工作仍在同一处。[继续已有工作](https://delta.dev/docs/agents/threads)

DeltaDB 持续记录消息、评论和文件变化，不要求每次记录都创建 Git 提交。官网描述这些细粒度变化具有稳定身份，可支持内容关联；评论在删除、移动和重写后的具体表现仍需实测。[官方介绍](https://delta.dev/)、[DeltaDB 与 Git](https://delta.dev/docs/concepts/delta-and-git)

### 用一个任务理解它的定位

下面是拟用于体验的示例，不是已经在 Delta 中执行的工作：修复“清空搜索框后，列表仍保持过滤”的问题。

| 工作时刻 | 在线程里留下什么 | 后来的人能接着做什么 |
| --- | --- | --- |
| 明确问题 | 复现步骤、期望结果、Agent 对代码的解释 | 知道改动要解决什么 |
| 决定方案 | 对方案具体段落的提问、修订与回答 | 理解约束和选择理由 |
| 实现 | 文件修改与测试执行记录 | 查看代码与验证依据 |
| 审查 | 具体位置的意见和审查结论 | 继续修订或检查尚未解决的问题 |
| 交付 | 项目选定的提交、发布或合并结果 | 找到最终结果和对应工作过程 |

这张表是阅读和体验的组织方式。评价时要分别检查“信息是否保留”“是否能准确跳到对应内容”“能否从原工作继续”，不能仅凭对话历史存在就判定整条关联已经成立。

## 官方已描述的能力

表中的“已有”指当前使用文档已经提供操作方式，本机安装版仍待核对。

| 能力 | 用户可以做什么 | 关键边界与来源 |
| --- | --- | --- |
| 针对对话评论 | 选中自己或 Agent 的一段文字，留下问题或修订意见 | 评论提交后交给 Agent，回答关联回原意见。[Comments](https://delta.dev/docs/agents/comments) |
| 针对代码评论 | 在文件或 diff 中选中代码留下意见 | 文件面板默认评论模式；直接编辑要切换模式。[Comments](https://delta.dev/docs/agents/comments) |
| 查看改动 | 在 Changes 选择上游分支、Last Commit、Last Turn 或某次提交 | 可以标记文件已看过；新增编辑会清除此标记。[Review & Sync](https://delta.dev/docs/agents/review-and-sync) |
| 独立审查 | 创建 Review 线程，阅读 Agent 生成的改动导读，提交通过或要求修改的结论 | 审查有独立工作副本，结论回到父线程。[Review & Sync](https://delta.dev/docs/agents/review-and-sync) |
| 多人协作 | 分享线程，共同查看、评论、编辑并指导 Agent | 项目线程分享需要仓库远端；执行环境随发送请求的参与者变化。[Collaboration](https://delta.dev/docs/collaboration/collaborate-thread) |
| 恢复与回退 | 重新打开原线程，或使用 Revert Conversation to Cursor 返回历史位置 | 回退会移除后续消息；只有仍对应该历史点的工作副本一起恢复，已经更换 checkout 的不恢复。[Threads](https://delta.dev/docs/agents/threads) |
| 子线程探索 | 从父线程开出单独对话，继承当时的上下文与文件状态 | 后续独立发展，结果和文件修改不会自动带回。[Threads](https://delta.dev/docs/agents/threads) |
| 子 Agent 委托 | 让父 Agent 分配独立调查或实现任务，查看子 Agent 的过程 | 默认 Worker、Reviewer 隔离工作，成功后自动带回修改；Scout 直接使用父工作副本。[Subagents](https://delta.dev/docs/agents/subagents) |

评论可以随下一条消息提交，也可以单独提交。一次留下多条针对具体内容的意见，能减少用户在主对话里逐段引用、解释位置的工作。这是建议最先体验的交互。[评论如何交给 Agent](https://delta.dev/docs/agents/comments)

Review 线程、普通子线程与子 Agent 的结果回传不同：Review 的文件修改通过父线程结论上的 Pull Changes 引入；普通子线程需要另行合并；隔离子 Agent 在成功完成后自动带回修改。提交审查结论本身不会合并代码。[审查](https://delta.dev/docs/agents/review-and-sync)、[子线程](https://delta.dev/docs/agents/threads)、[子 Agent](https://delta.dev/docs/agents/subagents)

## 把核心能力用明白

### 评论：将反馈放到具体内容旁边

Windows 中，可以选中一段内容后使用 Edit > Comment on Selection 或 `Ctrl+Alt+M`。在文件和 diff 的评论模式中，选中代码再打字也会创建评论。默认用 `Ctrl+Enter` 提交；发送快捷键受 Send With Modifier 设置影响。[评论操作](https://delta.dev/docs/agents/comments)

可以分别输入两条意见：“这里为什么需要缓存？”和“请保持现有排序规则。”体验时检查两条意见是否各自关联到所选内容，以及回答能否回到原意见。若要修改文件，先检查文件工具栏的评论模式按钮；评论与直接编辑是两个不同操作。

再让 Agent 在被评论的代码前插入内容、移动代码或重写函数。逐次观察原评论的位置、引用内容和回复入口。当前公开说明不足以给所有移动和重写情形作保证，这组操作用于测清实际边界。

### Changes：先明确正在比较哪段改动

| 比较范围 | 官方含义 | 适合回答的问题 |
| --- | --- | --- |
| 上游引用，例如 `origin/main` | 从与该引用的共同祖先开始比较 | 这条分支积累了什么工作？ |
| Last Commit | 当前未提交的改动 | 还有什么没有进入提交？ |
| Last Turn | 从上一轮 Agent 开始工作起的编辑 | Agent 这一轮具体做了什么？ |
| 打开的某次提交 | 该提交的改动 | 某次提交包含哪些内容？ |

Last Turn 的范围会持续到下一条用户消息。文件上的 Seen 标记属于当前审查者，文件新增编辑会清除标记。[比较范围与已看状态](https://delta.dev/docs/agents/review-and-sync)

体验时先在一轮工作结束后记录文件清单，再要求一次小修订。检查 Last Turn 是否切换到新一轮，以及已看标记怎样变化。判断 diff 是否正确时，先记录比较基准，避免把分支总改动与本轮改动混在一起。

### Review：审查讨论与父任务保持关联

从顶层线程输入 `/review`，或使用头部 Reviews 菜单。Agent 会生成按理解顺序组织的改动导读。读者可以评论、提出修订或在审查副本中尝试修改，最后通过 Submit Review 记录结论。[审查入口](https://delta.dev/docs/agents/review-and-sync)

需要分开观察三个结果：意见是否提交到父任务，审查副本里的代码是否改变，以及这些改动是否已引入父任务。Pull Changes 应用的是提交结论时保存的快照。体验时可先提交结论，再在审查副本追加一次编辑；比较第一次引入的文件与两次编辑，核对快照范围。追加编辑要带回时，先提交新的结论。

### 普通子线程、Review 和子 Agent 怎样选

| 形式 | 适用目的 | 谁继续处理 | 文件结果怎样回到父任务 |
| --- | --- | --- | --- |
| 普通子线程 | 从当前上下文探索独立问题或方案 | 用户与该线程的 Agent | 需要另行合并；消息回传也需显式请求 |
| Review 线程 | 检查已有工作并形成审查结论 | 审查者与审查 Agent | 通过结论保存的快照引入 |
| Worker 子 Agent | 委托一块独立实现 | 父 Agent 收集结果 | 默认隔离，成功后自动带回 |
| Reviewer 子 Agent | 委托 Agent 检查改动 | 父 Agent 收集结果 | 默认隔离，成功后自动带回 |
| Scout 子 Agent | 调查代码或信息 | 父 Agent 收集结果 | 默认使用父工作副本，终端产生的修改立即影响父任务 |

这张表描述默认配置。子 Agent 的工作副本模式可以调整；Scout 和 Reviewer 即使没有文件编辑工具，仍能通过终端修改文件。[子线程约定](https://delta.dev/docs/agents/threads)、[子 Agent 配置与文件访问](https://delta.dev/docs/agents/subagents)

体验普通子线程时，可以用 `/subthread`，并提出一个明确问题，例如“探索另一种修复方式，比较影响范围”。体验子 Agent 时，可以让父 Agent 委托“调查复现路径”与“检查测试覆盖”。这两组实验分别观察上下文继承、工作隔离和结果回传，不预先假定它们行为相同。

### 恢复、归档与回退怎样区分

| 操作 | 用途 | 应观察什么 |
| --- | --- | --- |
| 重开原线程 | 继续同一项工作 | 原讨论、评论和未提交文件是否仍在 |
| 归档再重开 | 整理线程列表后恢复工作 | 线程历史与工作副本重新可用的情况 |
| 回退到历史位置 | 回到先前的讨论和对应文件状态 | 后续消息移除、文件恢复和确认提示 |
| 新开独立线程 | 开始另一项工作 | 是否使用新的工作副本与起始代码 |

线程名或分支名相同，不代表接着原线程的未提交工作。归档保留线程记录；恢复受历史可用性影响。回退的具体 checkout 边界见前面的能力表。[线程生命周期](https://delta.dev/docs/agents/threads)、[工作副本恢复](https://delta.dev/docs/concepts/worktrees)

## Git、GitHub、Issue、PR 和 CI 各自起什么作用

Git 管理提交、分支和远端。GitHub 的 Issue、PR 和 CI 属于项目协作与交付渠道。DeltaDB 保存提交之间的工作过程；Delta 自己提供线程内讨论与审查。

| 对象 | 当前能确认的关系 | 尚不能据此认定的能力 |
| --- | --- | --- |
| Git | 代码项目要求 Git 仓库；结果可以交回本地仓库或来源远端 | Delta 的每一次编辑都对应一个 Git 提交 |
| GitHub Issue | 一个问题可以作为线程的工作目标；公开演示包含修复问题的流程 | 已有完整 Issue 管理界面、自动导入与状态同步 |
| GitHub PR | 官方支持让 Agent 推送分支、创建 PR，并按分享设置附上线程链接 | 所有 GitHub 审查意见都自动同步进 Delta |
| Delta Review | 在 Delta 内阅读改动、讨论并记录审查结论 | Delta 的审查结论自动等同于 GitHub PR 的 Review |
| CI | Agent 可以调用已有 CI 服务并检查结果；Land 结果卡可以显示 Agent 报告的状态 | 已有完整 CI 管理系统，或结果卡替代了实际 CI 证据 |

上述关系来自 [Delta 与 Git](https://delta.dev/docs/concepts/delta-and-git)、[PR 与 Land 流程](https://delta.dev/docs/agents/review-and-sync)及[公开测试发布说明](https://zed.dev/blog/delta-public-beta)。“尚不能认定”表示本次证据不足，不等于断言产品没有此功能。

官方公布的方向是让线程承接更多开发协作职责。Delta 自己的仓库已关闭 PR；Zed 社区仍保留 GitHub 流程，贡献者可以在 PR 中附上 Delta 线程。因此，研究 Delta 应重点观察它如何完成工作与审查，以及如何交付到现有仓库。[官方产品方向](https://zed.dev/blog/delta-public-beta)

### 怎样核实它对 GitHub 的实际支持程度

对于每项 GitHub 操作，记录“由哪个界面或工具完成”“使用哪个账号”“结果怎样关联回线程”。下面是待验证的问题，不是产品缺失清单：

| 场景 | 给 Delta 的示例请求 | 要核对的证据 |
| --- | --- | --- |
| 理解 Issue | “读取这个 Issue 的正文与讨论，整理复现步骤和验收条件。” | 实际读取工具、评论完整性、来源链接；是否存在专门的 Issue 入口 |
| 准备 PR | “基于本线程改动拟定 PR，列出目标仓库、基准分支和验证结果。” | 生成内容与真实 diff 是否一致，账号与目标是否明确 |
| 发布 PR | “按已确定的内容创建 PR，并关联本线程。” | PR URL、头部分支、提交、线程链接的访问条件 |
| 接收审查 | “读取该 PR 新增的审查意见，逐条说明对应改动。” | 普通评论、代码评论与审查结论的来源；自动同步还是一次工具读取 |
| 修复 CI | “检查该提交的失败任务，定位原因并验证修订。” | 运行链接、提交 ID、日志、修订后的新结果；是否只是 Agent 的文字报告 |

这组实验用于区分产品专门提供的功能与 Agent 利用当前环境完成的操作。能通过一次请求完成任务，并不直接证明存在后台同步、专门界面或持续状态跟踪。

### Land 按钮实际做什么

桌面版的 Land Changes 会创建专门的 Land 子线程，让 Agent 执行项目配置的 Skill。检查、合并方式和发布步骤由 Skill 定义。没有适用 Skill 时，它会提出配置流程，配置完成后仍需重新启动落地操作。网页端没有此入口。[Land Changes](https://delta.dev/docs/agents/review-and-sync)

Land Skill 的 frontmatter 需要 `metadata.delta-action: land`；文件夹或 Skill 名称叫 `land` 本身不足以让它出现在此流程中。若多个 Skill 符合条件，需要在 Land 子线程的斜杠菜单中明确选择。[Land Skill 配置](https://delta.dev/docs/agents/skills)

体验前先阅读项目已有的落地流程，列清测试命令、目标仓库、目标分支、合并方式以及发布步骤。执行后核对真实提交与 CI 运行，再比较父线程和 Land 子线程显示的结果。这里观察的是项目工作流怎样被承载和记录。

## 桌面与网页的区别

桌面发送的 Agent 请求可以使用当前机器的工作副本、终端工具与运行环境。网页中的 Agent 使用已同步的项目文件，没有本机 shell、checkout 或进程访问。对话和记录的文件变化会同步，运行中的服务器、环境变量和凭据不会随之同步。[执行位置](https://delta.dev/docs/collaboration/collaborate-thread)、[网页使用说明](https://delta.dev/docs/collaboration/delta-on-the-web)

因此，网页参与者能接着讨论、评论和审查；需要本机测试或构建的步骤，应在具备相应环境的桌面端执行。

### 多人协作时要分别观察数据与执行环境

可以由参与者 A 发起修改，参与者 B 留下两条具体评论并接着发送请求。记录两端出现消息、文件改动和评论的顺序，再让 B 使用一个只有 A 机器具备的资源，核对 Agent 怎样解释环境差异。

共享线程的草稿也会同步。发送请求会提交线程末尾待发送的各作者草稿；只在草稿中交流时尚未触发 Agent。由谁发送，也决定该轮使用的环境和模型用量归属。[共享草稿与执行规则](https://delta.dev/docs/collaboration/collaborate-thread)

网页端实验只验证读取、讨论、评论、审查与同步文件操作；网页请求没有终端。网页端使用托管模型，模型可用性也应作为实验条件记录。[网页执行条件](https://delta.dev/docs/collaboration/delta-on-the-web)

## 实际体验方案

用一个已有 Git 项目中的小问题走完整个过程，例如修复一个按钮行为。先确认本机 Delta 版本、账号和可用模型，并选择独立工作副本。以下结果均待实际记录。[首次任务指南](https://delta.dev/docs/getting-started/quick-start)

### 开始前准备

1. 记录 Delta 版本、操作系统、模型和提供方。模型连接在 Settings > LLM Providers 中配置；产品登录与模型可用性分别核对。[模型与提供方](https://delta.dev/docs/agents/models-and-providers)
2. 选择用于体验的 Git 仓库根目录。添加项目会把相关文件存到 Delta 的服务器；项目选择需要符合实际上传意图。[首次项目说明](https://delta.dev/docs/getting-started/quick-start)
3. 使用 Add Project 或 Open Git Project… 打开项目。在发送第一条消息前，通过项目菜单的 Work In 选择 Isolated Delta Worktree，并记录起始分支和 checkout 路径。[首次项目操作](https://delta.dev/docs/getting-started/quick-start)
4. 明确一个小问题的复现步骤、预期结果和项目已有测试命令。以下使用“清空搜索框后恢复完整列表”作为示例，实际体验替换为项目中的真实问题。

独立工作副本的新线程通常从远端默认分支开始，不等于当前本地工作目录中的代码。实际起点应在项目菜单和提交信息中核对。[起始代码选择](https://delta.dev/docs/concepts/worktrees)

### 完整流程速览

| 步骤 | 操作 | 要观察什么 |
| --- | --- | --- |
| 1. 开始工作 | 打开项目，让 Agent 先解释问题和拟定方案 | 起始分支、工作目录和原项目的关系 |
| 2. 评论方案 | 选中一段方案，问设计理由；再对另一段提出调整，提交评论 | 是否分别理解意见，回复能否回到原位置 |
| 3. 修改与验证 | 让 Agent 修改代码并执行项目已有检查 | 文件变化、执行过程与讨论怎样呈现 |
| 4. 审查本轮改动 | 在 Changes 选择 Last Turn，对具体代码发表评论并要求修订 | 改动范围、评论位置和修订后的关联 |
| 5. 独立审查 | 输入 `/review`，查看导读，提交 Request Changes 或 Approve | 父线程怎样显示结论，审查工作是否隔离 |
| 6. 带回审查修改 | 在审查中实际修改文件，再从父线程使用 Pull Changes | 引入的是结论时保存的修改快照；不是之后的编辑 |
| 7. 继续与协作 | 重开原线程；有合作者时分享并由对方继续一轮 | 未提交工作是否保留，执行位置和可用工具是否变化 |
| 8. 交付结果 | 按项目需要交回本地仓库、创建 PR 或执行 Land Skill | 交付目标、提交、线程链接和检查结果是否对应 |

评论、审查与交付入口见[评论说明](https://delta.dev/docs/agents/comments)、[Review & Sync](https://delta.dev/docs/agents/review-and-sync)；恢复与分享见[Threads](https://delta.dev/docs/agents/threads)、[Collaboration](https://delta.dev/docs/collaboration/collaborate-thread)。

回退另用一次可放弃的小改动体验：在历史位置执行 Edit > Revert Conversation to Cursor，比较剩余对话与对应文件状态。记录确认提示和 checkout 已更换时的表现。[回退约定](https://delta.dev/docs/agents/threads)

建议最先完成第 2、4、5 步。这组交互最直接体现 Delta 怎样把意见放在具体内容旁边，再把审查接回工作过程。这是体验顺序建议，不是产品能力声明。

### 可直接输入的示例与观察顺序

以下文字是本文编写的体验请求，不是 Delta 官方提示词，也不表示已经执行。将问题名称、路径和命令替换成项目真实内容。

**第一轮：确认问题与方案。**

> 当前问题是清空搜索框后列表仍保持过滤。请定位输入、过滤和列表更新的代码，解释复现路径，提出最小修改方案，并说明如何验证。先完成分析。

阅读回答后，对原因分析和方案各选一段发表评论。分别要求补充证据和保留现有行为，记录是否能准确从回答跳回评论。

**第二轮：实现与验证。**

> 按修订后的方案修改，并执行项目已有的相关检查。说明实际修改、命令和结果，指出仍未验证的行为。

打开 Changes，分别查看本轮范围和分支范围。在一处具体改动上要求解释或修订。将实际文件内容与 Agent 的总结对照，记录差异。

**第三轮：独立审查。**

启动 `/review` 后，可以继续要求：

> 重点检查清空输入、快速连续输入和列表内容更新时的行为。请结合代码和测试解释风险，并区分已经验证与尚未验证的部分。

检查导读怎样连接到代码；如果在审查中修改了文件，先记录父任务内容，再提交结论并引入修改。核对父任务在各个时刻发生了什么变化。

**第四轮：继续原工作。**

重开原线程后输入：

> 总结这项工作的目标、已完成修改、尚未处理的评论和验证结果，指出下一步。

对照之前记录，检查总结是否遗漏、误认未完成项或引用旧结果。另用一项可放弃的改动体验回退；恢复后的测试也要重新执行。

**第五轮：交付。**

先让 Agent 整理交付信息：

> 列出本线程要交付的文件与提交、目标仓库和分支、验证证据，以及尚未解决的审查意见。说明项目采用本地交付、PR 还是 Land Skill。

按项目实际选择完成交付。观察 Delta 怎样连接最终结果与原线程，不把示例请求中的选择当成已经发生的发布。

### 判断体验是否完成

体验完成需要留下事实，而不只是 Agent 的总结：能够定位两条评论及其回答，说明不同 diff 范围，区分审查结论与代码引入，重开后继续同一项工作，并找到实际交付结果。多人、GitHub 同步、历史边界等未执行项目继续保留为未验证。

### 每个场景怎样留下证据

每次记录包含：日期与版本、线程及角色、checkout 模式、操作前状态、实际操作、预期行为、实际结果、相关消息或提交链接。预期行为来自文档还是本次实验，也要写清。

| 场景 | 最少保留的证据 | 何时可以判定验证通过 |
| --- | --- | --- |
| 评论 | 目标内容、原评论、关联回答 | 能准确定位两端，修订后关联仍符合该场景预期 |
| diff 范围 | 基准引用、文件清单、对应编辑 | 所展示内容与选定范围一致 |
| Review | 父任务与审查副本的前后内容、结论事件 | 能区分意见提交、审查编辑和文件引入 |
| 子线程或子 Agent | 启动上下文、工作模式、消息与文件回传 | 回传与该模式的约定一致 |
| 恢复或回退 | 前后消息与文件、checkout 是否更换 | 恢复范围符合记录的前置条件 |
| GitHub 与 CI | Issue/PR 链接、提交 ID、运行日志 | 外部结果对应本次工作和具体提交 |

一次成功只证明记录条件下的场景。发生失败时保留实际错误和文件状态；未执行、前置条件不满足和行为不符分别记录，避免把它们混成同一种结果。
