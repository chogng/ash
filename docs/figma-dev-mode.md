# Figma Design 的 Dev Mode 与开发交接

Dev Mode 是 Figma Design 面向开发者的检查和交接方式。它让人和编码 Agent 获取设计里的布局、组件、变量、素材与实施说明，并让团队跟踪交接后的修改。它的重要性在于：设计能够成为实现的明确依据，后续调整也有可比较的版本。

对于无法进入付费模式的读者，下文从界面、实际操作和一个按钮的完整流程解释它。Figma 功能与方案范围依据 2026-10-06 的官方资料；对 Ash Design 的建议独立列在最后，属于产品建议，不表示已经实现。

| 读者关心的问题           | 本文的结论                                                               |
| ------------------------ | ------------------------------------------------------------------------ |
| 它和 Design 是什么关系   | 同一份设计文件的两种工作方式：编辑设计与检查开发信息                     |
| 为什么普通属性面板还不够 | 开发还需要组件来源、变量引用、实现关联、交接说明与设计变更               |
| 它如何帮助写代码         | 提供设计规格和项目组件关联，开发或 Agent 在项目中完成实现                |
| 它与 Make 有什么区别     | Make 在自己的工作区生成和运行应用；Dev Mode 服务已有设计与开发项目的交接 |
| Ash 值得借鉴什么         | 一份可检查的设计、明确的项目实现关联，以及持续的开发交接                 |

产品间的共同能力与区别见 [Dev Mode、Sites 与 Make 对比](figma-dev-mode-sites-make.md)。

## Dev Mode 与 Design 的关系

Dev Mode 与 Design Mode 使用同一份设计文件。Design Mode 主要用于制作和修改设计；Dev Mode 把查看方式组织成开发者需要的规格、组件、素材和交接信息。切换模式无需复制作品，也不创建另一份应用代码。它对团队的重要性在于：开发可以依据设计的结构和约定实施，而不必只从画面猜测。[Dev Mode 指南](https://help.figma.com/hc/en-us/articles/15023124644247-Guide-to-Dev-Mode)

## 界面和实际操作

进入 Figma Design 文件后，通过工具栏的 Dev Mode 开关或 `Shift+D` 切换。整体仍是左侧导航、中间画布和右侧面板，操作围绕当前选择展开。

| 区域         | 主要内容                                       | 开发者用它解决什么问题       |
| ------------ | ---------------------------------------------- | ---------------------------- |
| 左侧         | 已标记可开发的设计、画板及当前画板的图层       | 找到本次要实现的范围         |
| 中间         | 原有设计画布，选择和测量图层                   | 对照视觉结果，定位具体对象   |
| 右侧 Inspect | 对象属性、组件信息、代码、变量、素材和相关链接 | 获取实现所需的细节           |
| 右侧 Plugins | 开发相关插件与代码生成扩展                     | 接入项目使用的工具或输出格式 |

选择一个按钮后，右侧围绕这个按钮显示信息；选择它所在的容器后，查看范围变成容器。开发者可以从完整页面逐层进入具体组件。[Dev Mode 导航与检查](https://help.figma.com/hc/en-us/articles/15023124644247-Guide-to-Dev-Mode)

### 查看设计时可以做哪些修改

Dev Mode 的主要工作是查看和检查。组件 playground 的试验配置，以及 focus view 的临时尺寸和变量模式调整，不会把试验结果写回原设计；focus view 有单独的方案要求。标注、固定测量和交接状态则是共享协作内容，能否修改取决于对应席位与文件权限。[组件 playground](https://help.figma.com/hc/en-us/articles/5579474826519-Explore-component-properties)、[Focus view](https://help.figma.com/hc/en-us/articles/23919923330455-Dev-Mode-focus-view)、[标注权限](https://help.figma.com/hc/en-us/articles/20774752502935-Add-measurements-and-annotate-designs)

因此，理解它时需要区分“临时试着看”和“修改共享交接信息”。真正修改设计对象的布局、文字和组件定义，仍属于设计编辑工作。

## 如何检查布局与设计变量

Inspect 能提供布局、间距、颜色、文字、组件属性、样式和变量；画布测量可以显示对象距离。开发者据此判断容器和子对象如何组织，再采用项目自己的布局方式实现。[检查指南](https://help.figma.com/hc/en-us/articles/22012921621015-Guide-to-inspecting)

例如，一个按钮看起来是“蓝色圆角块加文字”，但实现时还需要知道：文字与图标的间距、按钮如何随文字变宽、使用什么字体，以及背景是否引用主题变量。前提是设计文件确实定义了这些信息；仅由几个自由摆放的图形组成的画面，不能凭切换模式获得完整组件和响应式规则。

变量尤其重要。Dev Mode 可以显示变量名称、所属集合、当前模式、值和别名关系，也能查看文件中的变量表。由此可以区分“这里恰好是某个蓝色”和“这里使用主操作背景变量”。后者能帮助开发在明暗主题之间保持一致。[变量检查](https://help.figma.com/hc/en-us/articles/27882809912471-Variables-in-Dev-Mode)

## 如何检查组件与状态

组件检查能提供主组件与实例的关系、组件属性和变体。Component playground 允许临时切换属性，观察不同组合，而不改变设计中的实例。[组件属性与 playground](https://help.figma.com/hc/en-us/articles/5579474826519-Explore-component-properties)

假设按钮组件定义了尺寸、禁用状态、图标显示和文字内容，开发者就能逐项试验这些配置。它帮助开发了解设计系统允许哪些变化；这里展示的是设计组件的配置结果，不等同于执行项目按钮的业务代码，也不会凭空补全未设计的 loading 或错误状态。

## 默认代码片段与 Code Connect

| 信息                  | 来源                                       | 应如何使用                     |
| --------------------- | ------------------------------------------ | ------------------------------ |
| 默认代码片段          | 从选中图层的设计属性生成                   | 理解布局和样式，再结合项目实现 |
| Code Connect 关联     | 团队建立的设计组件与仓库组件之间的对应关系 | 找到应复用的真实组件及其用法   |
| 编码 Agent 的代码修改 | Agent 结合设计上下文、仓库代码和任务生成   | 在项目中审查、运行并验证       |

默认片段可以选择 CSS、iOS 或 Android 相关输出，以及对应单位，也能使用代码生成插件。它提供的局部布局和样式不包含完整业务流程。[代码片段说明](https://help.figma.com/hc/en-us/articles/15023202277399-Use-code-snippets-in-Dev-Mode)

Code Connect 的价值是把“设计中的 Button”关联到“项目中的 Button”。团队还可以通过 CLI 定义设计属性与组件参数的对应及动态示例。比如把设计里的 Large 关联到代码 API 的 `large`，让开发或 AI 更容易采用已有组件。[Code Connect](https://developers.figma.com/docs/code-connect/)

UI 与 CLI 的呈现也有区别：UI 关联提供组件文件与名称，并支持 AI 代码预览；CLI 可以在 Inspect 中展示团队定义的组件使用片段。建立关联不能证明设计和代码始终一致，也不负责自动修改仓库。[UI 与 CLI 对比](https://developers.figma.com/docs/code-connect/comparing-cc/)

## 开发交接与版本变更

开发交接经常持续多轮：设计完成后，开发开始实现，设计又修改间距、内容或组件状态。Dev Mode 将交接状态、标注和版本比较放在设计旁边，帮助双方明确这一次依据什么实施。

| 能力            | 作用                                       | 需要注意的边界                           |
| --------------- | ------------------------------------------ | ---------------------------------------- |
| Ready for dev   | 标记设计已经可以由开发查看和实现           | 表达团队交接决定，不代表已生成应用       |
| Completed       | 标记该设计的开发工作完成                   | 表达工作状态，不等同于构建或测试通过     |
| Changed         | 对已交接或完成后又修改的设计提示变化       | 不是所有依赖变化都会触发                 |
| Compare changes | 比较设计版本的图层和属性变化               | 比较设计文件，不能代替项目的 Git diff    |
| 标注与固定测量  | 把设计原因、关键尺寸和实现要求附在对象旁边 | 必须由设计者明确提供，不能靠画面自动推断 |

Ready for dev 与 Completed 是交接状态；设计被修改时可出现 Changed。官方说明中，共享库更新实例、已绑定变量的值变化和已绑定样式的值变化等不会触发 Changed，因此没有提示不能当作所有依赖都未变化的证明。[状态与通知](https://help.figma.com/hc/en-us/articles/26781702258583-Dev-Mode-statuses-and-notifications)

Compare changes 支持并排和叠加查看，列出新增、删除及修改的图层，还能比较选中图层的属性和生成片段。例如按钮高度从 32 改到 36，开发者可以定位到变更处，而不必重新检查整张页面。[设计变更比较](https://help.figma.com/hc/en-us/articles/15023193382935-Compare-changes-in-Dev-Mode)

标注承载画面不能完整表达的要求。例如“这一区域应随内容增长”“图标按钮需要无障碍名称”“提交期间保留按钮位置”。这些是说明用途的例子，Figma 不会自动生成或验证这些约定。添加标注或固定测量需要 Full 席位及文件编辑权限；有 Dev 席位并能查看文件的用户可以阅读它们。[标注与测量](https://help.figma.com/hc/en-us/articles/20774752502935-Add-measurements-and-annotate-designs)

## 从按钮设计到项目实现的完整例子

以下是示例工作流程，参数和状态是示例设计的约定：

1. 设计者在 Design 中使用 Button 组件，设置尺寸与文字，定义正常和禁用状态，背景引用主题变量。
2. 设计者补充提交行为和无障碍要求，将所属画板标记为 Ready for dev。
3. 开发者在 Dev Mode 中检查布局、变量及组件状态；若有 Code Connect，找到项目中的组件与参数映射。
4. 开发者或编码 Agent 在项目中实现页面，接入业务状态，验证键盘、主题、尺寸变化和实际提交行为。
5. 设计者修改按钮尺寸后，开发者比较设计版本，并据此更新项目和重新验证。

Figma 负责提供设计及交接信息，项目负责实际行为和验证。状态记录让双方知道工作进展；它不能代替第 4 步。

## 方案和文件权限

完整 Dev Mode 需要付费方案中的 Full 或 Dev 席位。没有 Dev Mode 时，Design Mode 仍有基本检查能力，例如选择对象后按住 Windows 的 `Alt` 测量距离，通过菜单复制基本代码，以及在文件权限允许时查看属性和导出素材。[不同权限下的检查方式](https://help.figma.com/hc/en-us/articles/22012921621015-Guide-to-inspecting)

| 能力范围                                           | 官方方案与席位要求                               |
| -------------------------------------------------- | ------------------------------------------------ |
| Dev Mode 基本开发检查与版本比较                    | 付费方案，Full 或 Dev 席位                       |
| Code Connect                                       | Organization 或 Enterprise，Full 或 Dev 席位     |
| Completed、专门的 ready for dev view 与 focus view | Organization 或 Enterprise；开发操作需要对应席位 |

因此Professional 升级入口不代表升级后自动获得这里介绍的所有团队能力。Focus view 提供单项设计的集中检查、版本信息及临时尺寸或变量模式预览，它属于更高方案的能力。[Code Connect 要求](https://developers.figma.com/docs/code-connect/)、[Focus view 要求](https://help.figma.com/hc/en-us/articles/23919923330455-Dev-Mode-focus-view)、[Ready for dev view 要求](https://help.figma.com/hc/en-us/articles/23918228264855-Dev-Mode-ready-for-dev-view)

## Dev Mode 与 MCP 如何配合

Dev Mode 是开发者查看设计的界面，MCP 是让编码 Agent 获取设计上下文的通道。付费 Dev Mode 和免费远程 MCP对应不同的使用权限：远程 MCP 对所有方案和席位开放，免费方案有调用限制；桌面 MCP 需要付费方案中的 Dev 或 Full 席位。[MCP 可用范围](https://help.figma.com/hc/en-us/articles/35794667554839-What-s-new-from-Schema-2025)

MCP 的读取工具能够提供选定对象的设计上下文、结构概要、变量与样式、视觉参考以及组件代码关联。桌面服务器可以依据当前选区读取；远程服务器需要画板或图层链接来确定范围。这与只把一张截图发给 AI 不同：结构与命名信息也能作为实现依据。[MCP 工具](https://developers.figma.com/docs/figma-mcp-server/tools-and-prompts/)

MCP 返回的设计上下文可能呈现为 React 风格代码，但官方明确说明：它用于向 Agent 表达设计，不承诺提供可以直接上线的代码。编码 Agent 仍需采用项目的语言、组件和组织方式。[MCP 输出说明](https://developers.figma.com/docs/figma-mcp-server/server-returning-web-code/)

Code Connect、Dev Mode 和 MCP 可以配合，也可以分别使用：开发者可以手动检查设计；Agent 可以从链接读取设计；团队建立组件关联后，两者都能得到更明确的复用依据。

## 对 Ash Design 的产品建议

Ash Creator 的目标与当前能力分别由 [Creator 设计方案](../src/ash/sessions/contrib/creator/DESIGN.md)和 [Creator README](../src/ash/sessions/contrib/creator/README.md)维护。本节讨论 Dev Mode 对长期产品设计的启发，不把 Figma 的功能或以下建议写成 Ash 已有能力。

### 编辑和开发检查读取同一份设计

设计对象的层级、布局、组件身份、变量引用、素材版本及说明，应在所属设计内容中有明确表达。画布编辑、开发检查和 Agent 读取使用同一套内容与身份，开发面板显示从当前设计计算或读取的信息。

例如，背景绑定了主题变量，画布显示它的颜色，检查面板解释变量及其值，Agent 得到同一个变量引用。三处各维护一份可修改的颜色和组件信息，会让设计、检查结果与生成依据相互偏离。

切换查看方式只改变选择、导航和工具呈现。设计内容与撤销历史仍由设计编辑器持有，组件试验和开发检查的临时状态单独管理。这个区别决定了 Dev Mode 可以深入试验设计，同时保持正式作品的编辑过程清楚。

### 项目组件关联要明确表达

设计组件与代码组件分别表达设计和实现；对应关系需要说明设计中的身份、目标项目、代码位置、组件名称，以及必要的属性和值的对应。不能仅凭两个对象都叫 Button 就认定它们一致。

这种关系也不必要求同一组件只有一种实现。比如同一个设计按钮可以关联到 TypeScript 产品和 Rust 产品中的不同组件，各自说明使用方式。项目实现继续遵守各自的服务、主题、无障碍和测试约定。

设计中的属性改变以后，开发需要能判断原有映射是否仍然适用；映射本身不能证明项目代码已经采用该修改。默认样式片段、团队定义的组件使用示例与 Agent 的实际代码修改应明确标识来源，让使用者知道每项信息代表什么。

### Agent 使用的范围与版本要能追溯

将设计交给 Agent 时，请求应明确设计文档、依据的版本、选中对象及必要的组件、变量和素材信息。设计者继续编辑后，原请求仍应能说明当时依据的内容；新版本进入下一次任务时，再明确采用的变化。

项目代码拥有自己的版本。一次实现应能关联“根据哪版设计、修改了哪些代码、完成了哪些验证”，设计版本与代码提交不能互相代替。Agent 的输出是项目修改或设计编辑提案，采用时进入对应内容拥有者的编辑与历史机制。

对于尺寸、主题或组件库更新，检查入口应让人能查到相关引用；对外提供设计上下文的工具应与人看到的信息一致。只附一张图或不带版本的当前选区，难以解释任务执行期间发生的变化。

### 用实际开发任务判断能力是否完整

完整性应通过一项设计从编辑、交接、实现到再次修改的过程判断。下面是目标能力的验证场景，不代表现有测试已覆盖：

| 场景                       | 需要看见的结果                                     |
| -------------------------- | -------------------------------------------------- |
| 设计一个有文字和图标的按钮 | 可以检查布局关系、组件配置、主题变量与素材引用     |
| 临时试验按钮尺寸和状态     | 预览随配置变化，原设计与正式编辑历史保持原样       |
| 指定项目已有按钮组件       | 人和 Agent 都能定位目标组件，理解属性对应          |
| 将按钮所在画板交给 Agent   | 请求范围与设计版本明确，生成内容遵守项目契约       |
| 交接后再改尺寸或组件配置   | 可以比较交接依据与新设计，定位需要重新实施的部分   |
| 完成代码实现               | 在实际产品中验证主题、内容变化、键盘操作与业务状态 |

这些场景解释了 Dev Mode 为什么值得作为 Design 的完整能力看待：它把可编辑设计、可读的实施依据、项目组件复用和持续变更连接起来。代码显示面板承担其中的代码查看，不能独自完成整个开发交接过程。
