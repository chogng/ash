# 为什么 Ash 把上下文放进正文

2026-10-23 · 产品设计随笔

在 Ash 的聊天输入框里，文件、代码选区和日志可以成为正文中的附件标签。比如 `rust-analyzer (4-5)`：它占据消息中的一个位置，代表一份已经附加的内容，悬停可以看简短预览，点击可以打开选中时保存的完整快照。

我们有意把这些标签放在正文里。写给 Agent 的消息，经常需要把说明和材料穿插组织；材料出现在什么位置、前后分别说了什么，本身就在表达用户的意图。

## 材料的顺序也是表达的一部分

考虑一次排查问题的对话。我们有两段来自同一个语言服务器的日志，分别记录修改前和修改后的状态。仅仅附加两份材料，再写“比较这两份日志”，能表达比较任务，但还需要说明谁在前、谁在后，以及各自对应什么条件。

正文中的附件标签让这段说明可以直接这样写：

```text
这是修改前的输出：[rust-analyzer (4-5)]

修改配置后，输出变成了这样：[rust-analyzer (12-18)]

请比较这两段输出，解释新增错误与配置修改的关系。
```

读到“修改前”，紧接着就能看到它对应的材料；读到“修改配置后”，就能看到另一份材料。用户把比较对象、前后顺序和解释放在同一个阅读流程里。

附件栏也可以排序。正文内的标签进一步表达了材料与附近说明的关系：哪一份是依据，哪一份是反例，哪一段代码才是这句话要求修改的对象。这里的顺序既包含材料之间的先后，也包含材料与文字之间的相邻关系。

这正是 Ash 选择这种形式的原因。我们希望用户能够一边写说明，一边在需要的位置放入材料，组织出一条可以从头读到尾的消息。

## 标签让大段上下文成为可编辑的引用

代码和日志可能很长。把全文直接铺在输入框里，会挤开用户正在写的说明；只显示一个文件名，又不足以让人分辨普通文字与实际附加的材料。

附件标签提供了一个有明确边界的引用。它的外观告诉用户，这段文字绑定着实际内容；它在正文中的位置告诉用户，这份内容属于消息的哪一部分。

这也决定了它的基本交互：添加材料时插入到消息光标处；在标签前输入文字，引用位置随正文变化；删除引用时一并移除它绑定的上下文；撤销时恢复引用与内容快照。

引用身份需要与显示名称分开。同一个文件可以在消息中出现多次，每一次都可能指向不同的选区或不同时间保存的内容。仅凭两个标签的名称相同，不能把它们合并成一份材料。

标签压缩的是界面占位，实际附加的内容仍然占用上下文预算。

## 顺序需要一份确定的内容

“先看这段日志，再看那段日志”的前提，是两段日志的内容在查看和发送之间保持确定。

如果点击标签时重新读取当前日志，语言服务器可能已经追加了新的输出；如果重新读取文件，用户可能已经修改了代码。标签的位置没有变化，它指向的材料却变了，这会破坏原先组织好的比较关系。

因此，文件和代码选区引用要绑定保存下来的内容。对编辑器选区，Ash 在添加到 Chat 之前捕获选中的文字和来源范围；这份快照用于后续查看、草稿保存与发送。日志选区也沿用这条链路。之后原文件或输出发生变化，已有引用仍然代表当时选择的内容。

标签显示可读的来源名称与行范围，例如 `rust-analyzer (4-5)`。内部通道 ID 留给资源身份使用，避免占满正文。检查内容则分成两个动作：悬停看短预览；点击标签，或在引用处按 Alt+Enter，在只读编辑器中查看完整快照。

只读标签页可以保留在旁边，方便继续检查长内容。同一个引用重复打开时复用已有标签页，查看动作保留聊天草稿，不会发送消息。

## 文件职责可以与 VS Code 对齐

这个产品选择并不要求重新发明所有编辑器能力。引用范围、装饰注册、主题配色、悬停与选区绘制，都可以沿着已有的 Editor 和 Workbench 职责组织。

对照本地 VS Code 源码时，需要区分两条链路：它既有正文中的内联引用，也有独立附件区域。`chatInputReferenceDecorations.ts` 服务于内联引用装饰；独立附件区域的主要组合与渲染逻辑位于 `chatInputPart.ts` 的 `renderAttachedContext()`，具体附件控件位于 `chatAttachmentWidgets.ts`。

所以，对齐时应比较职责、调用方与生命周期。不能因为没有一个单独叫“附件栏”的文件，就把产品差异简化成少了一份源码，也不能据此认定相关能力已经全部对齐。

| 职责                     | Ash 的归属与对齐方式                                                         |
| ------------------------ | ---------------------------------------------------------------------------- |
| 引用状态、范围跟踪与撤销 | `ChatDynamicVariableModel` 承担对应的引用模型职责，继续拥有 Ash 的快照绑定。 |
| 内联引用的装饰样式注册   | `chatInputReferenceDecorations.ts` 与 VS Code 的同名职责对应。               |
| 引用的主题配色           | `chatColors.ts` 定义主题颜色，由编辑器装饰系统消费。                         |
| 输入组件组合             | `ChatInputPart` 承接输入与附件生命周期，保留 Ash 的正文内展示方式。          |
| 正文中标签的呈现和操作   | `ChatInputEditor` 与内联附件控件拥有 Ash 的展示、点击和键盘交互。            |
| 范围背景、换行与选区绘制 | 继续由通用编辑器基座负责。                                                   |

共享职责可以沿用对应文件与契约；正文内附件带来的展示职责保留明确的 Ash owner。这样的对齐既方便沿源码定位问题，也能保留我们选择这套输入体验的原因。

## 让可见顺序贯穿发送链路

界面表达的顺序，还需要与实际发送的顺序分别核对。

正常插入路径会按正文中的引用位置排列附件，草稿也会保存引用的起止偏移。发送时通过 `Promise.all` 解析这些附件，将引用位置和快照一起保留，不会因为某个文件先读完就把它排到前面。

Code 和 Cowork 的发送模型保留未经裁剪的正文，让这些坐标在提交前仍然有效。`ChatService` 沿正文切分文字，并把每个标签替换为对应的附件输入。略去 Skills 等额外输入后，可以这样理解：

```text
正文中的编辑顺序：
说明一 → [引用 A] → 说明二 → [引用 B]

提交给 Agent 的输入顺序：
说明一 → 上下文 A → 说明二 → 上下文 B
```

普通发送、排队和运行中补充输入（steering）使用同一套组装逻辑。同一个名称出现多次，也会按各自的位置提交各自的快照。图片保留为图片输入，文件和日志保留为上下文输入；引用名称不会再作为一份重复的正文附在末尾。

旧草稿或来源上下文如果没有正文位置，仍然放在消息前面。有效文字片段保留原有的缩进和换行，纯空白间隔不生成单独的文本输入。若保存的引用范围越界或互相重叠，提交会明确报错，保留草稿供用户恢复，避免把错误位置的文字当作标签替换掉。

Rust 后端按输入顺序生成持久化记录，再按相同顺序组装模型消息中的文字、上下文和图片部分；附加的文件与日志继续标明为数据。模型的上下文预算与压缩仍由后端处理，附件标签并不会免除上下文成本。

正文内标签让用户能够把材料放在说明旁边，查看确切的快照，并在同一份草稿里组织上下文。提交链路保留这条阅读顺序，让用户排好的材料关系也能出现在模型输入中。
