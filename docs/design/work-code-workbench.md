# Work / Code 工作台与文档编辑器目标设计

> 状态：目标设计，部分基础已完成。当前只有 Code 工作台，Academic 已通过文档贡献接入，共享模型、严格读取和旧存储迁移已完成。普通文档类型、Work 界面组合、Chat 主画布及 Agent 文档修改尚未实施。本文用于后续修改 Ash Desktop 的 Workbench 与 Stanza Editor；当前实现以 [Workbench 装配说明](../workbench.md)、[Stanza 目录说明](../../src/ash/editor/README.md)和[富文档设计](../../src/ash/editor/document-engine.md)为准。本文不宣称 Work 界面组合已经存在。

## 结论

Ash Desktop 保留一个安装包、一个 Workbench 和一套编辑器内核，当前固定提供 **Code**，未来 **Work** 的界面组合由产品入口负责。入口决定默认布局、主要入口和专用工具；资源类型决定打开哪个编辑器。两种界面组合都能在同一窗口以标签打开代码文件和结构化文档，切换标签不重载窗口。

**Chat 是 Work 的主要入口，也是 Code 可使用的 Agent 对话能力。** 用户可以只聊天，也可以在同一对话中讨论或修改代码、文档；会话与对话由同一套服务管理，不按 Chat / Work / Code 分成三类，也不随界面变化复制。Academic 已从顶层模式退出，作为 Code 及未来 Work 中的论文文档类型；其标题、摘要、引用等规则保留在 Academic 文档配置中，普通文章不继承这些规则。

| 维度           | Code                               | Work                           |
| -------------- | ---------------------------------- | ------------------------------ |
| 默认主画布     | 代码文件、差异与工程任务           | Chat 或当前文档                |
| 默认辅助内容   | 文件、终端、测试、调试、Agent 对话 | 文件、文档大纲、资料与 Chat    |
| 文档与代码文件 | 均可打开；按资源类型选择编辑器     | 均可打开；按资源类型选择编辑器 |
| Chat           | 编码任务的对话入口，也可只聊天     | 一般对话和文档任务的主要入口   |
| 专用工具       | 代码相关贡献                       | 文档与研究相关贡献             |

Work 和 Code 是同一 Desktop 产品内的不同界面组合，不改变 [`ash code` TUI 与 Desktop 的产品线边界](../product-lines.md)。

## 用户行为契约

### 打开与切换

1. 当前产品固定打开 Code；未来增加 Work 界面入口时，继续通过现有生命周期保存工作副本和窗口状态，不在共享 Workbench 中增加模式切换协议。未保存内容不得因界面改变丢失。
2. 用户在任一界面组合打开代码文件时使用代码编辑器，打开普通 Work 文档或 Academic 文档时使用文档编辑器。打开另一标签只改变活动编辑器，不更换产品入口。
3. “使用其他编辑器打开”只列出能安全处理当前资源格式的视图。同一资源同时出现多个可写视图时，它们必须使用同一个模型和工作副本；不得各自读取文件并形成两份待保存内容。
4. `.txt`、`.md` 与结构化文档是不同的持久格式。把纯文本或 Markdown 变成富文档是显式“转换为文档”操作，创建新的结构化资源；原文件内容和扩展名保持不变。将来若支持同一 Markdown 文件的双向编辑，须另定义可往返的格式规则和不支持语义的处理方式。

### 新建与保存

1. “新建文档”在 Work 和 Code 中均创建带有普通文档类型的未命名输入，打开文档编辑器。保存时选择结构化文档扩展名，例如 `.ash-doc`；“新建文本文件”继续创建纯文本输入。
2. 普通 Work 文档打开时使用通用结构规则：段落、标题、强调、列表、引用、链接、表格和图片。空文档直接进入正文，不强制出现论文标题或摘要。
3. Academic 文档继续使用其论文结构、引用与文献功能。普通文档和 Academic 文档各有稳定的类型与协作兼容标识；更改扩展名不能悄悄改变文档规则。
4. 文档保存、另存为、回退、自动备份和外部修改冲突由 Workbench 工作副本处理。一次用户编辑由 `TextModel` 提交一个版本和对应撤销记录。格式、对象和文本必须一同保存与恢复。

### Chat 与工作内容

1. Work 在没有打开资源时突出 Chat；打开文档后，文档是主画布，Chat 可以与其并排。Code 以编辑器为主，Chat 仍能用于编码任务。Work 的主画布由自身的界面组合装配共享 Chat 界面，普通 Workbench 不引用 Code Sessions 的专用窗口界面。
2. 对话可以没有项目或文件，也可以关联代码库、文档或其他明确资源。聊天本身不要求编辑目标；同一对话讨论的资源改变时，不重新创建另一类会话。
3. 两种界面组合访问同一会话与对话身份。界面变化可以改变当前展示位置，但不能复制会话、消息或附件状态；用户能够重新找到原对话。界面入口不单独决定 Agent 的操作权限，具体操作取决于会话上下文、可用能力和用户授权。
4. Chat 对代码或文档的修改须经过对应的文件或文档编辑契约，并遵守版本和冲突规则。Chat 界面不直接写入编辑器内部状态，也不单独保存另一份内容。

## 所有权与装配

| 内容                                     | 唯一负责方                                 |
| ---------------------------------------- | ------------------------------------------ |
| 文本、文档语义、版本、选区与撤销         | `src/ash/editor` 的 `TextModel` 与文档命令 |
| 代码或文档编辑界面的输入、焦点与呈现     | 对应的编辑器控件                           |
| 文件类型选择、标签、工作副本、保存与冲突 | Workbench 编辑器与文件服务                 |
| 产品身份、默认布局、启动装配与窗口创建   | Code 产品入口；Workbench 接收装配数据      |
| 会话、对话和 Agent 执行                  | 现有 Chat / Sessions 契约与 App Server     |

两种界面组合共用 `TextModel`、文件服务和 Chat 契约。产品入口在启动时静态声明可用的代码与文档编辑器，不在运行中卸载贡献。Code 的测试、调试等工具与 Work 的文档工具分别由各自入口装配；打开文件不会加载另一套完整工作台。Work 的 Chat 主画布复用共享 Chat 组件，由 Work 的界面组合负责摆放与焦点；共享布局机制不嵌入 Work 专用分支。Academic 的结构规则由文档配置组合，不能写进通用编辑器内核。

通用文档和 Academic 文档由同一个文档编辑器入口管理。当前每个配置都指向同一个 `DOCUMENT_EDITOR_ID`；增加配置时应由一个注册入口维护完整配置集合，并按文档类型选择，避免重复注册编辑器 ID。新文档的备份内容类型也应来自选中的文档类型，而非固定使用 Academic 内容类型。

## 持久化与迁移

- 产品入口负责界面装配；当前 Desktop 固定启动 Code Workbench，Agents 为独立页面。未来 Work 的界面入口应按实际产品职责设计，不引入工作台模式注册表或 `workbench.mode` 设置。
- 旧 `workbench.mode` 配置不再影响启动，保留用户 JSONC 中的其他设置和注释；旧 `configuration.json` 的搬迁继续由 profile owner 处理。
- 原 `academic` 工作台状态已按 key 合并到 `code`，冲突源项保留。未来增加 `work` 时，须明确打开资源、未保存工作副本和窗口状态的恢复规则；布局若与 Work 不兼容，可以按 Work 默认布局重建，但不能删除未保存内容。状态留在工作台状态存储。
- 新结构化文档使用自描述的文档类型和格式版本，并在读取时严格校验。现有 Academic v1 文件需有一次性读取迁移；新写入只生成目标格式。纯文本和 Markdown 的导入由显式转换命令负责，不作为结构化文件解析失败后的隐式读法。
- 文档文件中的图片使用受文档拥有的稳定资源身份；显示尺寸与位置由编辑器计算，不把浏览器节点或临时 URL 当成持久数据。

## 编辑体验与边界

通用文档的第一版以连续正文为目标：居中限宽、清楚的段落层级、文本格式工具栏、文档大纲，以及完整的键盘、输入法、剪贴板和撤销行为。纸张尺寸、分页、页眉页脚、脚注、修订追踪和 `.docx` 往返不属于第一版。以后加入分页时，页面是对文档内容的排版结果，不把页界写成正文结构。

新建和修改的所有可见文案进入现有本地化系统，至少用一种非默认语言验证。编辑区、工具栏、列表、表格和切换命令可由键盘完整操作；焦点切换有可见反馈，弹层关闭后恢复焦点。文档编辑器提供无障碍帮助，复杂视觉内容提供可阅读的文本视图，并让用户控制帮助提示的播报。状态变化使用适当的屏幕阅读器提示，避免同一事件重复播报。

## 当前基础与实施入口

共同编辑器注册、严格结构化读取、共享资源模型和唯一工作副本已经接入。`DocumentEditorTextModelService` 按规范化资源持有 `TextModel`／`DocumentWorkingCopy`，多个视图用引用计数管理生命周期；冲突文档类型拒绝打开，关闭一个视图不销毁另一个视图。备份内容类型跟随所选文档类型，另存为必须转移资源与工作副本身份。

Academic 由扩展声明选择可信 factory，共享同一文档 pane；Code 共同装配代码与文档编辑器，代码匹配排除已注册结构化文档。旧 Academic 模式及中央模式注册表已经退场，`ash.academic.storage` 到 `ash.code.storage` 的逐 key 迁移保留冲突。上述基础不能视为普通文档、Work 界面或 Agent 结构化编辑已完成。

具体剩余动作和依赖顺序统一维护在 [Work / 通用文档 TODO](../../TODO.md#work--通用文档--todo)：先升级自描述类型／格式，再闭合普通文档、Agent 编辑和 Work／Chat 界面流程。本文继续定义目标行为、所有权及验收要求。分页、`.docx` 和 PDF 输出分别另行设计与验收。
