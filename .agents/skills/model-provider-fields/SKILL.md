# 模型字段的多 provider 对比

用户提出增加或变更模型字段时，先交付有依据的多 provider 对照和建议，让用户能判断采用哪个字段、类型和语义。即使请求只提到 GPT 或 Codex，也要检查其他 provider 如何表达同一能力，不能直接把单家字段当成 Ash 的通用契约。

## 定位现有契约

从用户要表达的能力开始，检查现有字段、生产调用方和测试，明确本次是模型事实、接入限制、请求参数、账户权益、用户偏好还是 Ash 执行策略。

- [通用模型声明规范](../../../crates/model-provider-info/docs/model-template.md)：第 2 节是各家接口对照，第 7 节是当前缺口，第 8 节是 Codex 字段映射。设计建议和已实现能力必须分清。
- [model-provider-info README](../../../crates/model-provider-info/README.md)：静态目录、字段归属和当前可解析格式。
- [models.json](../../../crates/model-provider-info/models.json)、[解析声明](../../../crates/model-provider-info/src/static_model_spec.rs)及生成的 [Schema](../../../crates/model-provider-info/models.schema.json)：核对准确型号和已有契约，不手改生成文件。
- [models-manager README](../../../crates/models-manager/README.md)：动态目录、来源合并和连接生效规则。
- [套餐与价格](../../../docs/models/plans-and-pricing.md)：涉及订阅档位或账户权限时读取；运行时权益仍以所选连接的实际证据为准。

按字段用途继续追踪 `ash-api` 的请求和响应编码、`model-provider` 的调用、Core 的执行或 App Server 与客户端的使用。相邻 Codex 源码可用于解释 Codex 字段及消费者，但不能替代其他厂商的接口证据，也不能把 Codex 的执行策略当成跨 provider 标准。

## 对比其他 provider

以 Ash 当前模型目录为范围，检查其他 provider 的同类能力，包括 GPT、Claude、Gemini、GLM、Kimi、Grok，以及目录中相关的 DeepSeek、Meta 等条目。名称相同不证明语义相同，名称不同也不证明不能统一。只深入本次能力相关的参数和调用链，不重复整理全部接口。

对照按具体型号、协议和接入区分；公开 API、订阅接入、第三方兼容端点分别核对。记录以下差异：

- 官方请求字段及 JSON 位置、单位、允许值、默认值，以及它影响请求还是返回内容。
- 型号支持范围、参数组合条件、上下限，以及省略、`null`、`false`、`none` 等值各自的含义。
- 模型规格与当前接入能力、账户权益的差异；未知、明确不支持和 Ash 尚未实现分别标注。
- Ash 已有对应字段、请求编码和实际消费者，以及此次变更会影响的客户端和持久配置。

新增外部事实或涉及可能变化的规格、套餐、价格时，核对最新官方文档或官方源码，附直接链接及核对日期。现有总结表是检索入口，不能把旧表当作最新证据。无法确认的差异标为“待确认”，不要编造支持范围或从型号前缀推断能力。

## 给用户的结果

先用一句话说明推荐的 Ash 字段、类型和理由，再给出紧凑对照表。表格围绕本次决策，可按需要合并列：

| Provider／型号／接入 | 官方字段及语义 | 值、默认及使用条件 | Ash 当前支持情况 | 依据 |
| --- | --- | --- | --- | --- |

若存在多种合理设计，再比较候选方案的字段名、类型、能表达的差异及代价。说明为何选择布尔值、枚举、数值、列表或结构，以及默认行为和未知状态；不要只说“统一字段”或“更灵活”。

建议必须回答：

- 哪些语义能作为共享字段，哪些需要按型号或接入单独声明和编码？
- 事实、偏好和执行策略各由谁维护，谁验证并实际使用？
- 是否已有字段可表达需求，新增字段是否存在具体消费者？
- 改名或改变语义时，哪些配置、协议、生成类型、UI 和测试需要同步？

用户只要求评估时，交付比较与建议。用户已明确选择或授权实现时，沿用已有授权推进，不重复要求确认。存在影响正确性的未定语义时，先给出具体选项和差异，再请求所缺的决定。

## 设计判断示例

**上下文容量与长上下文偏好**：先比较各型号的默认容量、最大容量和所选接入限制。容量用数值描述；只有存在更大可用容量时，开启／关闭的用户偏好才适合布尔值。固定容量或未知容量不能因属于某个 provider 就获得开关。具体 token 数留在目录和测试中，不在 skill 中固定。

**推理深度与摘要**：先比较各家的模式、深度档位、思考预算和返回内容。GPT 的 `reasoning.summary = none` 表示不请求摘要，不能据此设计成所有 provider 通用的“关闭推理”。相近能力可以有统一业务字段，但请求编码和允许值必须保留协议及型号差异。

**加速与账户权益**：先区分服务等级、速度参数和高速型号路由，再核对订阅权限。不能因为某家有 `priority`，就让其他 provider 发同一个字段；模型声明支持某档，也不能证明当前账户有权使用。

**执行策略字段**：比较 `comp_hash`、审批模型或专用型号分类时，先查其真实消费者。压缩历史兼容标识需要保存、恢复和切换时的判断；审批模型需要明确 provider、模型及连接。只增加空字段或复制某家固定值，不构成完整支持。

## 实现后的同步

按本次变更更新现有通用模型声明规范中的对应比较和实现状态，不复制整张表到 skill。字段契约、调用方、配置迁移、生成 Schema／客户端类型及受影响验证按仓库规范同步完成；未实现或未验证的部分明确标注。
