# VS Code TypeScript API 与浏览器样式职责对齐

以 `../vscode/src/vs` 为只读参照，让 Ash TypeScript 中明确对应 VS Code 的文件、公开契约、职责和真实调用链可以逐项定位。上游只用于确认结构和可观察行为；实现与测试必须由 Ash 独立编写，禁止复制、批量同步、逐行翻译或轻微改写上游代码。

## Learnings

* 对齐前必须先判定文件关系、真实生产调用链和唯一 owner；同路径已有文件只做可归因的局部修改，缺失文件只在调用链实际到达时原路径创建并同步迁移 import，仅 Ash 文件在未获决定前不动。上游只提供公开契约和可观察行为证据，不能把文件清单、成员差异、私有实现或批量数量当作实现蓝图；一旦无法说明每个改动如何闭合当前行为链，就停止写入并回退本批越界变化。
* 已知跑偏根因是把只读审计结果当成实现队列、把公开契约对齐当成私有结构模板、再用批量文件数代替行为进度。三者会共同制造无调用方文件、整文件重写、平行 owner 和品牌替换式 CSS；必须由批次准入与真实行为测试阻断，而不是事后靠类型检查修补。
* 上游证据必须分层使用：文件路径和公开声明决定落位，生产调用方决定实施顺序，测试和实际运行决定行为目标；上游私有方法、DOM 层级和 CSS 声明不决定 Ash 的实现。若把这四类证据混成一次文件复制，即使名称、类型检查和截图都通过，也仍然是假对齐。

## 写代码前的批次准入

每批开始修改前，先写出一条可核对的短记录：

```text
用户行为 → Ash 生产调用方 → 本批公开 API/文件 → 唯一实现与状态 owner → 可观察结果 → 定向测试
```

然后锁定本批允许修改的准确路径，并为每个路径记录：`双方都有 / 仅 VS Code / 仅 Ash`、生产调用方、唯一 owner、预期动作和验证。未进入清单的路径本批只能读取；中途发现新依赖时，停止写入并重新执行准入，不能顺手创建文件、改 CSS、改外围 contribution 或整理相邻代码。已有文件的预期动作必须具体到本批职责和 diff hunk，不能写成“按上游对齐”或“整体重构”。

并逐项确认：

- 生产调用方真实存在，不是测试、示例、类型引用或上游调用方；
- 文件存在关系已分类，缺失文件会落到准确同路径，已有文件会保留未涉及代码并原地修改；
- 所需下层依赖已经就绪，链上没有尚未取得用户决定的仅 Ash 载体；
- 下层公共契约和 registry 不反向导入 contribution，`import type` 也计入依赖检查；文件无 DOM 或已有文档描述都不能证明职责正确。文档与依赖规则冲突时先修正原文，并把代码现状记为待迁移；用户已明确确认的专属能力仍按其确认范围处理，不能据此扩大通用职责；
- 旧入口、旧 import 或重复 owner 能在同批退出，不需要临时桥、别名或新旧 API 并存；
- 由注入容器创建的长期对象遵守 [TypeScript Frontend Architecture](../../../.github/instructions/frontend-architecture.instructions.md) 的构造注入规则。对齐的是“创建 owner、依赖可见性、作用域和失败语义”，不是只补 `@I...Service` 语法；若 Ash 的实例化底座尚不能根据参数装饰器解析依赖，必须先闭合该下层缺口，不得用 options、service locator、手写空依赖描述或对象内部的替代容器模仿上游外形；
- 实现方案来自 Ash 当前 owner、状态和生命周期，不复刻上游私有类图、DOM 层级或控制流；
- 至少一个测试能从真实入口观察状态或副作用，并能证明现有行为没有退化。

任一项答不出来时，本批只能继续只读调查或登记台账，不能先写声明、空文件、转发方法或外围 contribution。批量数量只在这张记录成立后用于迁移同类调用方；“一次至少十个”不是同时探索十个 owner，也不是按文件数凑进度。

## 上游证据读取顺序

对每个候选端口，必须按以下顺序读取证据，不能先通读上游实现再反推本地结构：

1. 先读 Ash 的生产调用方、现有 owner、相邻实现和行为测试，写出当前状态、输入、副作用和释放边界。
2. 再读上游同路径文件的 imports、exports、公开声明和注释，只记录外部契约与职责。
3. 再读上游直接生产调用方和测试，提取触发条件、可观察结果、错误与生命周期语义。
4. 只有公开契约和测试仍无法解释某个行为时，才查看解决该歧义所需的最小上游实现片段；只记录行为事实，不记录或复刻其私有类、字段、方法分解和控制流。
5. 关闭上游实现视角，回到 Ash owner 独立写出实现说明后再编码。若实现说明仍能与上游私有结构逐项对应，停止并重新设计。

不得把 `diff`、复制后的临时文件、逐行翻译稿或批量替换结果作为实现草稿。公开签名可以精确对齐，私有实现必须能仅凭 Ash 状态模型和已记录的行为事实解释。

## 跑偏停止与纠正

出现以下任一信号时立即停止本批所有写入：用户指出“自己造了”“像抄的”“效果变差”“代码风格失序”；新文件没有 Ash 生产调用方；已有同路径文件被大面积替换却无法逐项说明行为必要性；CSS 或 DOM 只是把上游品牌词换成 Ash；类型检查通过但真实入口、owner 或可观察结果仍说不清。

停止后先以本批开始时保存的工作树为基线，只读列出本批触及的准确路径，并把每个路径归入以下一类：

- 当前闭合调用链必需的同路径局部修改；
- 当前闭合调用链必需且满足创建条件的上游同路径缺失文件；
- 没有生产调用方、owner 不成立、整文件重写、复制式 CSS 或与当前行为无关的越界变化；
- 批次开始前已存在或来源不明、必须保护的用户变化。

不得在错误方向上继续追加 wrapper、适配层、CSS 覆盖或“整理”补丁。对第三类变化只能精确撤销本批自己的改动，执行前再次核对不会覆盖第四类变化；涉及删除文件仍遵守准确路径确认。然后回到用户行为入口，重新选择一个依赖闭合的最小切片，通过行为测试后才能恢复批量迁移。纠正报告必须说明触发错误的决策和被违反的门禁，不能只描述代码表面症状。

## 对比规则

文件和公开 API 使用同一条非对称规则。先批量完成整个目标目录的对比，再按下表决定落位；只有进入当前依赖闭合切片的项目才能修改，目录清单中的其他差异只进入台账：

| 对比结果 | 行动 |
| --- | --- |
| VS Code 有同路径文件，Ash 没有 | 当当前调用链确实到达该职责时，先在对应路径原地创建文件并对齐公开 API 名称与职责，再由 Ash 独立实现逻辑；同批把现有调用方的 import 迁到该文件并补测试，不另建替代路径。若尚无本地生产调用边或下层 owner 未就绪，只记为待补，不提前创建。 |
| 双方都有同路径文件 | 只在原文件中修改本批对应的公开契约、职责、生命周期和可观察行为，并同批迁移调用方；保留未涉及的 Ash 行为，不整文件删除重写，不为对应职责另建文件，内部实现由 Ash 独立设计。若无法把大范围替换中的每一部分关联到当前行为链，默认缩小为局部修改。 |
| Ash 有，VS Code 没有，且尚无用户决定 | 暂停修改并一次性报告完整清单，由用户决定保留、改名、迁移或删除。 |
| Ash 有，VS Code 没有，且已有用户决定 | 按已记录的决定处理；确认作为 Ash 专属归属的文件或 API 可以继续承接其职责。 |
| 只有内部实现不同 | 不要求同名或同算法，只验证职责边界与可观察行为。 |

“公开 API”包括跨文件使用的导出、公开成员、服务契约、注册标识、配置键和回调契约，不包括只在文件内部使用的私有辅助代码。用户对仅 Ash 文件或 API 作出决定后，将路径、确认职责和处理方式写入当前对齐台账；除非职责、公开契约或调用方发生变化，后续批次不重复询问。

文件是否存在于 VS Code 只决定是否需要用户确认，不决定 Ash 的最终职责归属。VS Code 已有的对应职责必须直接回到其同路径文件；该文件在 Ash 缺失时不需要另行确认，可原地创建。只有 VS Code 不存在、拟由 Ash 新增的专属归属才必须先提交路径和职责供用户决定。Ash 专属职责应回到用户已确认且符合仓库依赖方向的 Ash 专属归属。一个文件混合两类职责时，只迁移对应职责，不为文件数量机械搬运全部实现。

文件存在关系只回答“代码最终放在哪里”，不能回答“现在先做哪个文件”。实施顺序由当前用户行为入口和生产依赖链决定：先找入口，再确认唯一 owner，沿依赖向下找到最小可验证端口，完成后才向上迁移调用方。上游存在但不在当前调用链上的文件，不得因为缺失、同名或看起来相关就创建；尤其不能从外围 contribution 反向制造尚未对齐的控制器、命令或状态载体。

## CSS 与 DOM 边界

- CSS 纳入生产文件集合审计，但同路径只说明样式职责位于对应组件，不代表选择器、声明或主题变量可以复制。VS Code 有而 Ash 缺失的 CSS 只形成行为待补项；先确认本地 DOM owner、状态 class、主题 token 和布局契约，再独立实现。
- 对齐可观察行为包括焦点、选区、禁用态、高对比度、换行、滚动和几何结果；不对齐上游产品品牌。Ash 创建并拥有的 DOM、CSS root、内部 class、动画名和主题变量必须使用 Ash 词汇，禁止新增 `monaco-*` 或 `--vscode-*`。
- 发现本地 CSS 与上游完全一致或只做品牌替换时，将其记为上游实质代码并停止扩散。保留已有许可证；不得继续复制、逐行翻译或通过替换前缀伪装成本地实现。任务需要修改时，只独立实现本批行为并用真实 DOM 与计算样式验证。
- CSS 完成不能只靠文件存在、构建或截图。必须同时核对组件 owner、选择器命中的本地 DOM、状态投影、主题 token、高对比度和至少一条真实浏览器行为链。

## 对齐不变量

- 对应实现使用准确的相对路径、文件名、大小写、公开名称、签名和 owner 模块。文件拆分、状态 owner、生命周期、调用顺序、副作用和错误语义都属于契约；只对齐导出或成员名属于假对齐。
- VS Code 存在而 Ash 缺失的生产文件和公开 API 都属于待补项，不以文件数量、成员数量或类型检查结果代替实现。
- 同一运行环境和生产调用路径中的一个公开职责只能有一个入口、一个实现和一个状态 owner。现有 Ash 实现已承担对应职责时，直接迁移或重命名该实现并同批更新全部调用方；不得新增同名外壳、继承外壳、转调类、别名、聚合导出或新旧 API 并存。
- 每个修改批次必须形成依赖闭合的调用切片，顺序为基础契约与命令 → 纯操作 → 状态控制器 → 运行环境入口 → contribution；不能按成员差异数量随机挑文件。新对齐的文件若仍需依赖上游不存在且尚未确认保留的仅 Ash 载体，立即停止实施并先对齐下层 owner；例如标准 `ICommand` 链不能新增对仅本地 `editorEditCommand.ts` 的依赖。
- 只有运行环境、职责、输入语义或生命周期确实不同才拆开实现；多个公开契约共享同一机制时，共享逻辑仍只保留一份并由正确层拥有，不能复制实现或状态。
- VS Code 不是内部设计上限。满足对应职责和可观察行为后，保留或改进更简单、清晰且适合 Ash 的数据结构和控制流，不为形似上游增加无用状态、分支或抽象。
- 遵守 `base → platform → editor → workbench → code` 的依赖方向；`sessions` 可以依赖 `workbench` 及更低层，`workbench` 不得依赖 `sessions`。`common` 不引入浏览器、Node 或 Electron 环境能力。
- 发现仓库已有上游实质代码时，保留其许可证与来源信息并停止扩散；不得删除许可证头来伪装成本地实现。

## 独立实现门禁

同路径和公开名称只决定代码放在哪里、外部如何调用，不能决定 Ash 的内部类图、私有字段、私有方法顺序、DOM 层级、控制流或文件内排版。开始写代码前必须先用本地证据完成一份最小实现说明，至少包含：当前状态 owner、DOM owner、输入事件入口、布局/坐标来源、生产调用方、释放边界和能够证明现有行为的测试。任一项不清楚时只继续调查，不开始修改。

允许从上游提取的事实仅限：文件路径、公开名称与签名、owner 职责、调用方依赖能力、可观察行为和测试场景。禁止以下做法：

- 按上游的类拆分、私有成员、方法排列或控制流逐项搭骨架，再替换名称或压缩代码；
- 用 public-member diff、文件差异数、待补成员数或“每批文件数”驱动实现顺序；这些数据只能用于调查，不能作为设计或完成指标；
- 为了让上游 API 或 CSS 容易接入，先改变 Ash 的状态 owner、DOM owner 或滚动/焦点/布局模型；owner 变化必须先由本地行为证据证明必要性，并作为独立依赖切片验证；
- 把类型检查通过当成方向正确。类型检查只在本地行为设计成立后验证契约，不能替代 DOM、输入、布局、生命周期或视觉效果验证；
- 以批量速度为由写长行、密集内联对象、压缩私有方法或偏离目标目录现有 Ash 风格。代码组织先与相邻 Ash 文件保持一致，再满足公开契约。

独立性的反向检查：如果计划中的实现可以通过“复制上游 → 改 import/前缀/类型 → 格式化”得到，或私有结构与上游一一对应，就必须停止并重新从本地 owner 与行为设计。正确示例是保留 Ash 已验证的单一滚动状态和 DOM owner，只在其准确 owner 上补标准公开入口；错误示例是为了得到同名构造函数，把上游 scrollbar 类图和 DOM wrapper 整体移入 Ash。

用户要求大批量时，批量大小只约束已经证明方向正确后的机械迁移。第一条涉及新 owner、DOM 层级、输入链或布局模型的切片必须先单独通过真实行为验证；验证前不得扩散到十个调用方。用户指出“像复制”“效果变差”或“代码风格失序”时，立即停止当前批次，先精确回退本批新增变化并重新审计，不能继续补丁式修饰现有方向。

### 变更归因与代码质量门禁

写完最小切片后、扩大批量前，逐个 diff hunk 标记为以下四类之一：`公开契约对齐`、`生产调用方迁移`、`Ash 独立实现`、`行为测试`。不能归类的 hunk 立即移出本批；一个已有同路径文件若出现与当前行为无关的 import 重排、私有成员重排、注释替换、格式清洗或样式重写，视为整文件重构信号并停止扩大。

代码质量不是行为完成后的装饰。公开声明的分组、顺序和命名可以在不改变 Ash owner 的前提下贴近上游契约；私有代码的缩进、换行、命名和方法粒度必须与目标目录相邻 Ash 文件一致。完成前必须运行仓库适用的 formatter/linter，并人工检查 touched diff：禁止为了批量速度写超长 import、单行条件、密集对象字面量、无意义缩写或仅转发一层的方法。若本地实现比上游更难读、效果更弱或调试路径更长，该项保持待处理，不能以“API 已存在”计为完成。

## 端口准入门禁

上游公开成员差异是待调查清单，不是实现队列。一个端口只有在修改前能够写出完整的 `生产调用方 → 公开端口 → 唯一 owner → 状态变化或副作用 → 可观察结果` 链路时才能实现；链上任一段不存在，就保留在台账中，不通过新增方法制造链路。测试、示例、类型引用和成员比较脚本不算生产调用方。

逐项执行以下判断：

1. 先找 Ash 中需要该能力的生产调用方；没有调用方就停止，不写空端口、预留 API 或仅为成员报告归零的转发方法。
2. 核对上游成员实际返回或控制的对象由谁拥有，再核对 Ash 同名文件是否拥有同一种对象。若上游 facade 拥有整体容器，而 Ash 同名类只拥有其中的轴、画布或状态投影，禁止返回父组件 DOM、借用相邻对象或为对齐签名重做本地 DOM 层级；先沿当前行为链对齐真正 owner，不能成立时记为 `owner 不兼容`。
3. delegate 类端口必须同时满足：下层已有唯一且可验证的真实操作、同批有生产调用方迁入、行为测试能证明事件到达该操作。禁止为同名而暴露私有 handler、增加无调用方的二次转发或复制上游 wrapper。
4. 如果当前候选因 owner、调用方或下层依赖未就绪而停下，返回当前用户行为链寻找下一项基础依赖；禁止横向跳到另一个“差异较少”的文件继续清零报告。

端口实现后的完成标准不是“方法存在”，而是生产调用已经经过该端口、旧入口退出、唯一 owner 产生预期状态变化，并由行为测试观察到结果。无法满足时必须明确报告阻塞层和下一项下层依赖，不能把声明或类型通过计为部分完成。

## 同路径批量调查

用户指定目录或同一目录下多个文件时，把完整目录当作一个查询批次。首次只读检查应批量取得：

- 本地与上游的生产文件集合、同路径、仅本地、仅上游和大小写差异；
- 对应文件的 imports、exports、公开声明和直接生产调用方；
- 浏览器目标涉及 CSS 时，本地 DOM 创建点、root 与状态 class、主题变量、同路径 CSS 的上游实质代码相似性；
- 上游直接调用方、相关测试以及本地现有行为测试。

优先使用一次目录审计、带多个模式的 `rg`、循环读取或等价批量工具。输出过大时按“文件集合”“符号与调用方”“测试”拆批，不能默认退化为逐文件查询。批量调查不扩大修改或删除权限。

## 工作流程

1. 修改前保存 `git status --short`、tracked diff 和未跟踪文件清单，区分任务创建、用户已有和来源不明的改动；来源不明默认保护。
2. 读取涉及层的 reference，确定本地根目录、VS Code 根目录、目标目录、必要调用方和层级验证入口。
3. 建立对应表，记录文件与公开 API 是“双方都有”“仅 VS Code”还是“仅 Ash”，以及符号路径、owner、职责、调用链、生命周期和行为差异；浏览器目标另记 DOM owner、CSS root、状态 class 和主题 token。
4. 把上游 imports 当作依赖能力清单，先画出“基础契约与命令 → 纯操作 → 状态控制器 → 运行环境入口 → contribution”的生产调用链，再沿缺失或错误 owner 深度优先追踪；一条依赖分支未闭合、或链上仍出现尚未确认的仅 Ash 载体时，不开始修改、不铺开不相关分支，也不添加临时桥接文件。
5. 完成“独立实现门禁”的本地实现说明，并从真实用户行为、上游测试或缺陷路径核对触发点、状态变化、坐标语义、副作用、错误与释放顺序。先写清哪些本地 owner 保持不变、哪些公开契约需要改变；不得先按上游私有结构写骨架。
6. 对首次涉及新 owner、DOM 层级、输入链或布局模型的最小切片先实现并运行真实行为验证；未通过前不扩大批次、不迁移外围调用方。
7. 最小切片验证通过后，按文件存在关系落位：仅 VS Code 文件先在同路径原地建立公开契约，再独立实现并迁移 import；双方已有文件直接原地修改。随后把现有实现和状态收敛到唯一 owner，统一名称、参数、返回值、枚举、配置键和回调契约。
8. 同批更新必要调用方、测试和当前架构文档；用定向行为测试证明本地实现。CSS 变化还要用真实浏览器检查 DOM class 与计算样式，不把文件存在、类型检查或截图当作完成证据。

当本地一个文件承担上游多个文件的职责时，把 VS Code 对应职责迁回准确 owner；Ash 专属职责迁回已确认的 Ash 专属 owner。发现尚未记录决定的仅 Ash 文件或公开 API 时，完成本批只读清单后暂停并请求用户决定，不能自行保留、改名、迁移或删除；已有决定的项目按记录继续处理。

## 删除确认

任何文件删除都必须在执行前取得用户对准确路径清单的确认。清单需要说明删除原因、VS Code 对应情况、剩余生产调用方数量和 Git 可恢复性。目录、glob 或此前的概括授权不能替代本次确认；清单变化后必须重新确认。

等待确认期间可以继续不改变候选及其调用链的只读调查，但不能删除、移动隐藏文件或继续实施依赖该删除决定的修改。

## 验证

- 修改前后重新比较完整目标目录；仅 VS Code 的文件和公开 API 应减少，新出现且尚无决定的仅 Ash 文件或公开 API 必须暂停并请求用户决定，已有决定的 Ash 专属归属必须符合其确认职责。
- 浏览器目标运行 CSS ownership audit；完全相同的上游 CSS、重新出现的上游产品 root、新增的 `monaco-*` 或 `--vscode-*` 都必须阻断完成。品牌替换后仍与上游一致的 CSS 必须列入待清理报告，不能作为已对齐证据。
- 逐项复核 imports 的符号和 owner 路径，并用 `rg` 检查旧名称、错误大小写、别名、重复入口、并行实现和聚合导入。
- 确认旧公开入口和旧状态 owner 已无生产调用方，新的公开契约实际走向唯一现有实现，而不是新增一份实现。
- 至少验证一条受影响的真实行为链，覆盖触发、owner、状态变化、副作用和释放。
- UI 对齐必须在 Ash 与上游执行同一组语义场景，逐项记录输入、焦点/选区/滚动/布局状态、主题状态和结果。Ash 结果缺少上游已有状态、产生退化或只能靠静态截图看起来接近时，不得标记完成；截图只用于留证，不能代替 DOM、事件、计算样式和几何断言。
- 优先运行仓库定义的最小类型检查和能够直接触发受影响职责的定向行为测试。结构审计、成员名比较和类型检查都不能代替行为测试；报告必须列出实际运行的测试及其覆盖行为。检查配置必须禁止输出，生成产物的构建或测试配置必须把 `outDir` 放在源码树外。
- 最后复核对应表、`git diff` 和 `git status`，分别报告真实对齐、仍是假对齐、缺失 owner、范围阻塞和未解决验证失败。
