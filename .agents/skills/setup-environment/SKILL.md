# Set up Ash

Run commands from the repository root.

## Inspect before installing

1. Record the checkout path, commit SHA, OS, architecture, setup target, and initial `git status --short`.
2. Take commands from the current [justfile](../../../justfile) and [package scripts](../../../package.json). Do not copy VS Code's Gulp setup, lockfiles, or build commands into Ash.
3. Check required tools at known executable locations before installing; avoid filesystem-wide scans and environment dumps.

Read versions on every run; do not maintain another version list in this skill or a bootstrap script:

| Input | Authority and use |
| --- | --- |
| Git and ripgrep | [Build prerequisites](../../../docs/build.md#构建入口): check `git --version` and `rg --version` for checkout and repository tooling. Product-packaged search executables are separate locked resources. |
| Just | [.just-version](../../../.just-version) pins the formatter version; [justfile](../../../justfile) owns the recipes and [setup-just](../../../.github/actions/setup-just/action.yml) installs the CI version. Check `just --version` matches the pin and `just --list` parses the current file. |
| Rust | [rust-toolchain.toml](../../../rust-toolchain.toml): channel, profile, and components. Inspect `rustup toolchain list` before running a command that might implicitly install a toolchain. |
| Node | [.nvmrc](../../../.nvmrc) for direct Node execution; `engines` and `devEngines.runtime` in root `package.json` for package-script execution. Compare them and stop on contradictions. |
| pnpm | Root `package.json` → `packageManager`; confirm the actual executable version. Ash's preinstall rejects a different package manager/version. |
| Bun | Root `package.json` → `devDependencies.bun`, resolved by [pnpm-lock.yaml](../../../pnpm-lock.yaml); workspace dependency used for single-run, no-emit type checking. |
| TypeScript and browser tools | Root and workspace `package.json` files plus `pnpm-lock.yaml`. `@ash/typescript-compiler` supplies `tsc` for emit/watch; the `typescript` alias supplies the JavaScript compiler API. Playwright and Electron also come from workspace dependencies, not global installs. |
| Python | [scripts/pyproject.toml](../../../scripts/pyproject.toml) → `requires-python`; execute the chosen interpreter to print `sys.executable`, its version, and import `tomllib`. On Windows, a discovered `python` command may only be an App Execution Alias. |
| uv | [scripts/pyproject.toml](../../../scripts/pyproject.toml) → `tool.uv.required-version`; confirm `uv --version` matches. |
| Python tools | [scripts/pyproject.toml](../../../scripts/pyproject.toml) declares dependencies; [scripts/uv.lock](../../../scripts/uv.lock) locks their versions and hashes. [scripts/install_python_tools.py](../../../scripts/install_python_tools.py) syncs with `--locked` and binary distributions only. |
| Other build/runtime inputs | Owning build code, `third_party/*/runtime-lock.json`, and [.devcontainer/Dockerfile](../../../.devcontainer/Dockerfile) for the Linux reference package set. Install a host tool only when the selected execution path needs it. |

For frontend-only setup, do not install Bazel, signing tools, GPU/media tools, or product sandbox services.

## Preflight resources and permissions

Check CPU availability (including worker/container quotas), physical/available memory, swap or memory pressure, and free space on both the checkout/output filesystem and tool-cache filesystem. Use macOS `sysctl`, `memory_pressure -Q`, `vm_stat`, `df`, and `iostat`; Linux `nproc`, `/proc/meminfo`, cgroup limits, `df`, and disk metrics; Windows CIM CPU/memory queries and `Get-PSDrive`. Report unavailable observations.

Check active builds before starting Cargo/V8/media builds. Run heavy Cargo, package preparation, and Electron acceptance sequentially when resources are shared. Set `CARGO_BUILD_JOBS` only in the invoked process, within its CPU/memory budget; respect an existing lower limit. Keep the repository Playwright worker count.

Use process-local PATH and interpreter overrides. Preserve shell profiles, user tool configuration, compiler flags, proxy settings, and existing `CARGO_TARGET_DIR`. Do not alter ACLs/setuid permissions or install privileged services. Do not record credentials in the skill, scripts, logs, or environment files. [`.codex/environments/environment.toml`](../../../.codex/environments/environment.toml) is generated by Codex: use a supported environment tool if requested and available, never hand-edit it or claim a saved environment was created without confirmation.

## Install only missing inputs

- **macOS:** inspect the selected Xcode Command Line Tools/compiler (`xcode-select -p`, `xcrun --find clang`). Reuse Homebrew if installed for missing tools; do not install Homebrew just to bootstrap Ash. Full backend preparation builds the locked LiveKit source on macOS; check `go version` against the requirement in [build/lib/livekit.py](../../../build/lib/livekit.py) and the locked source's `go.mod`, and ensure `tar` plus the system C/C++ toolchain are available. Its `GOTOOLCHAIN=local` setting requires a compatible installed Go toolchain.
- **Windows:** use the target architecture's Visual Studio Developer PowerShell with MSVC, Windows SDK, and the English tool language pack described in `docs/build.md`. Check `pwsh` supports the current Just Windows shell's `-CommandWithArgs` before invoking ordinary recipes. Reuse installed Build Tools; install missing components through the existing installer or `winget`. Resolve Python with `python`/`py`, and pass the selected executable explicitly if needed. Locate LLVM/libclang and set `LIBCLANG_PATH` only for the build process when the selected dependency requires it; do not set global `CC`/`CXX`.
- **Linux/cloud:** identify the distribution and package manager before installing OS packages. Use the current `.devcontainer/Dockerfile` to identify libraries for the selected scope. Workspace installation can build `native-keymap` even for Web and needs the C/C++ toolchain, `pkg-config`, X11 and xkbfile development libraries. Backend paths additionally need the applicable ALSA, SSL, libcap, DBus, GTK, Wayland and xkbcommon development libraries; [Bubblewrap's build](../../../crates/bwrap/build.rs) requires `libcap` discoverable through `pkg-config`. Chromium dependencies must match the locked Playwright version. A headless worker can verify Web; Electron requires a display/session or an existing Xvfb setup plus its runtime libraries. Missing kernel namespaces, sandbox support, or privileges are blockers, not reasons to disable isolation.
- **Existing Dev Container:** inspect `.devcontainer/devcontainer.json`, Dockerfile, and `post-create.sh` before using it, then verify tools including uv and `scripts/.venv` rather than assuming post-create completed. Its lifecycle changes ownership and Electron helper permissions and enables privileged mode; do not run `post-create.sh` directly on a host or silently reproduce those actions in a cloud worker. Reuse an already provisioned container's tools and mounted caches. Creating/changing that container requires authorization covering its privileges.

Backend dependency builds can require CMake (the current locked `aws-lc-sys` dependency uses it); check `cmake --version` when preparing that scope. Install libclang, NASM, Ninja, or source-build toolchains only when the selected dependency path requires them. Ordinary V8 and Sherpa preparation uses checksum-locked precompiled archive/binding or library inputs through [scripts/cargo.py](../../../scripts/cargo.py) and the owning build entrypoints. Preserve explicit caller overrides; do not opt into source builds to work around missing archives. Bazel is optional: if selected, use Bazelisk with [`.bazelversion`](../../../.bazelversion), and set process-local `BAZEL_SH` to Git Bash on Windows as described in `docs/build.md`.

For Node and pnpm, reuse an installed version manager or the documented pnpm standalone installer with the version read from `packageManager`. Inspect any installer for profile/global changes before executing it. Do not use an unpinned `pnpm dlx`, global npm install, or assume Corepack is installed.

For Rust, install missing channel/components from `rust-toolchain.toml` through rustup. Compare `rustc -vV` and `rustup target list --installed` with the selected [build target](../../../build/lib/targets.py); install a missing target for that toolchain when needed. Windows development packages select MSVC, so the Rust target and Visual Studio tools must match. Fetch dependencies with `cargo fetch --locked`; build and test commands are in [Rust validation](../rust-development/SKILL.md#validation).

For Python, install the required uv version and run `just install-python` with the inspected bootstrap interpreter, for example `just --set python /absolute/path/to/python install-python`. If Just or its required shell is not available yet, invoke `scripts/install_python_tools.py` directly with that interpreter, as [frontend CI](../../../.github/workflows/frontend.yml) does. The installer syncs `scripts/.venv` from the committed lock with `--locked`, reusing a compatible environment. It retains the selected interpreter and does not download Python or build dependencies from source. Do not update the lock or add ad hoc pip requirements to hide a setup failure. If an existing environment uses an incompatible interpreter or is broken, report it and repair within the authorized scope; do not delete it automatically. Afterward, verify the repository interpreter runs and imports `tomllib`. Just selects `scripts/.venv`; Node's [build/python.ts](../../../build/python.ts) also uses it unless a process-local `PYTHON` explicitly overrides it. On Windows, Node otherwise selects `scripts/.venv/Scripts/python.exe` even before it exists, so complete Python initialization before frontend protocol hooks.

Install JavaScript workspace dependencies with `pnpm install --frozen-lockfile`. The install can build Electron-related dependencies even for Web; check compiler/runtime prerequisites and resource cost first. Retain [pnpm-workspace.yaml](../../../pnpm-workspace.yaml) build-approval rules. Do not enable all dependency builds, skip integrity checks, or update lockfiles to hide a setup failure. Install the locked Chromium only when browser acceptance needs it: `pnpm exec playwright install chromium`. On Linux, inspect missing OS libraries before the privileged `install-deps` action.

Node-gyp and `electron-rebuild` do not use `build/python.ts` to discover Python. If their discovery fails, pass the verified interpreter through process-local `PYTHON` for the install/rebuild command; on initialized Windows checkouts, use the absolute path to `scripts/.venv/Scripts/python.exe` instead of an App Execution Alias.

After installation, verify `./node_modules/bun/bin/bun.exe --version` against the declared dependency. Use this pinned executable directly (the package uses `bun.exe` on every platform); do not install a separate global Bun. If its executable is missing, inspect pnpm's install output and the existing `allowBuilds.bun` rule before retrying installation.

## TypeScript checks

For single-run type checking, invoke the pinned Bun directly: `./node_modules/bun/bin/bun.exe check -p <tsconfig> --all`. Run the owning preparation command first when generated inputs are missing or stale; reuse preparation for unchanged inputs. Use `pnpm typecheck:*` only when its full lifecycle is needed, not as a forwarding layer for an already prepared check. Keep emit/watch on their owning compiler entrypoints.

When the selected build or test already prepares and checks the same inputs, let that lifecycle run once instead of preceding it with a standalone typecheck. Use direct checks for validation that no selected build or test covers.

Within one CI job, prepare generated inputs once before the dependent checks. For build-tool tests after `node build/prepare.ts`, compile the scenario runner with `pnpm --dir test/scenario compile`, then run `pnpm --dir build run test:prepared`; the normal build test entrypoint retains preparation for standalone use. Reuse only artifacts available in that job; another runner needs its own preparation or a verified artifact transfer.

## Select and verify the scope

If no target is specified for a headless worker, use the Frontend/Web tier. On a fresh checkout, frontend `pre*` hooks may compile Rust protocol generators. Reuse a verified protocol cache/package when available; do not fabricate generated files or symlink outputs from another dirty checkout.

| Tier | Preparation and acceptance |
| --- | --- |
| Frontend/Web without backend | `pnpm test:smoke:browser` builds Web and checks Renderer and automation types. To reuse an existing build, check `test/automation/tsconfig.json` through `./node_modules/bun/bin/bun.exe check -p test/automation/tsconfig.json --all` if needed, then use `pnpm test:smoke:browser:no-compile`. Launch with `pnpm dev:web` only if requested. |
| Backend/CLI | Run `just verify <package>` and the owning build (for Code, `just build-code`). Complete backend package preparation uses `just ash-package`. |
| Full Web | `pnpm test:smoke:browser:full` checks frontend types, builds Web and prepares the packaged-Node backend. Launch with `pnpm dev:web:full` only if requested. |
| Desktop | `pnpm test:smoke:desktop` prepares the backend, builds Electron and checks Renderer and automation types. Launch with `pnpm dev` only if requested. `pnpm test:smoke:ui` selects UI acceptance but still prepares the backend runtime package for startup metadata. |

For a setup smoke check, select scenarios under [test/smoke/areas](../../../test/smoke/areas) using the package script's file/filter arguments. Confirm at least one applicable test ran and inspect skips. For accompanying TypeScript changes, use [TypeScript validation](../../../.github/instructions/typescript-testing.instructions.md).

Reuse successful preparation for the same inputs through the matching `:no-compile` smoke script. These scripts skip lifecycle preparation; they do not replace a missing Web/Electron build, backend package, automation typecheck, or browser installation.

For planning without compilation or installation, use `just --dry-run install-python` and `just verify ash-utils-home-dir --plan`. Do not pass made-up dry-run flags to installers, lifecycle hooks, or backend resolvers.

## Reentry, failures, and handoff

On rerun, inspect current versions, lockfiles, cache validity, and completed tier results before repeating work. Reuse the same profile/features and output layout. Do not automatically run `pnpm clean`, Cargo cache pruning, store deletion, `git clean/reset/stash`, or permission changes. Cache cleanup requires a separate request and stopping affected processes.

Retry only after correcting the failed stage. On a permission or download failure, report the required access or unavailable source; do not bypass access controls, disable integrity checks, or substitute an unverified mirror. Stop only processes started by this setup; use their handles/PIDs and await exit. Tests use repository fixtures and isolated profiles; do not launch against the user's live Ash profile.

Report checkout/SHA, resolved versions and sources, installed or reused inputs, process-local overrides, commands/exit codes, tests executed/skipped, blockers, and stopped or intentionally running processes. Review `git status` for unexpected generated or lockfile changes. Do not update README/CONTRIBUTING or tool configuration as a routine final step.
