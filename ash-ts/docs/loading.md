# 正式产物加载基线

本基线用于决定功能加载边界，不把单个 chunk 小于 500 kB 当作启动性能目标。

## 重现

在仓库根目录运行 `corepack pnpm --dir ash-ts test:loading`。
脚本构建正式 Web 产物，启动本地 App Server，使用 Playwright 重复测量三次。

- 每次使用独立浏览器；在初始窗口就绪后禁用 HTTP 缓存，再重新导航测量启动。
- 在同一窗口依次测量首次打开代码文件、PDF、终端面板，体现增量加载成本。
- 报告写入 `.build/desktop/playwright/test-results/*/loading-baseline.json`，同时作为测试附件保留。
- 下一次 Playwright 运行会清理该测试输出目录；需要跨版本对比时先归档报告。
- `build-metrics.json` 记录各入口静态 JS 闭包、模块清单和动态导入；`build-assets.json` 单独记录 worker、WASM、CSS 等资源体积。

## 测量边界

| 场景 | 就绪标准 |
| --- | --- |
| 启动 | 页面完成加载、后端 API 已连接、工作台与编辑器区域可见，再经过两帧 |
| 代码 | 单击文件树打开 `main.ts`，输入区域挂载且首行文本可见 |
| PDF | 单击 `paper.pdf`，首张 canvas 可见且具有非零尺寸 |
| 终端 | 显示面板，xterm 可见且进程状态为 running |

耗时包含 Playwright 调用和轮询成本，不等于纯前端执行时间。ScriptDuration、TaskDuration
来自 CDP 主渲染线程计数，另列报告，不包含 worker CPU。PDF 的标准是首张画布就绪，
不是完整文档加载或像素正确性的证明。终端标准不包含 shell 提示符出现时间。

网络记录来自 CDP 页面目标；响应字节包含 HTTP 开销。worker 请求可能有开始事件却没有
此目标上的完成事件，因此 `bytes: null` 表示未观测到完成，不是零字节，也不一定仍在下载。
需要结合构建资源清单分析 worker；不能把表中观测到的字节合计当作整个浏览器的完整下载量。

环境为本机 loopback HTTP、未压缩静态文件、浏览器进程与 OS 文件缓存已热。
本基线不是冷进程启动、真实网络或 Electron 启动性能测量。跨版本必须使用同等环境。

## 首次记录：2026-09-15

macOS arm64，Chromium 149.0.7827.55，三次测量。以下为中位数，体积使用十进制 MB/kB。

| 场景 | 操作到就绪 | 主线程脚本 | 主线程任务 | 此阶段已观测完成的响应字节 |
| --- | ---: | ---: | ---: | ---: |
| 启动 | 839 ms | 122 ms | 235 ms | 4.263 MB |
| 首次代码 | 216 ms | 100 ms | 204 ms | 37.5 kB，另有两个 worker 请求未计入 |
| 首次 PDF | 211 ms | 126 ms | 195 ms | 428.2 kB，另有 PDF worker 请求未计入 |
| 显示终端 | 50 ms | 11 ms | 26 ms | 无新增请求 |

### 已确认的加载事实

- Web 工作台入口静态 JS 闭包约 2.205 MB，但启动还立即加载 Code 模式及其他动态模块；只看静态闭包会低估首屏成本。
- 终端面板尚未显示，xterm 相关文件已经在启动阶段请求。其核心 JS 产物约 341 kB；“使用了动态 import”不代表“等用户使用才加载”。
- PDF 主实现约 425 kB 的 JS 在首次打开 PDF 时才请求，已经具备延迟加载边界。
- PDF worker 独立产物约 2.206 MB。它不在单 chunk 限额里，也没有包含在上表 PDF 完成响应字节中。
- 代码编辑器实现已经随 Code 模式启动加载；首次打开文件主要增加模型、DOM 和 worker 初始化成本。

## 下一步决策

隐藏终端初始化已按下节修复并复测。代码编辑器是否延迟，需要比较空窗口与直接打开文件两种
启动方式；本轮不预先决定拆分。PDF 已延迟，不为了满足统一数字进一步切碎。

本轮保留现有 chunk 检查，没有根据这三次本机采样新增耗时硬门禁。入口、动态功能、worker
应分别建立预算；需要更多同条件样本和目标环境数据后，再确定阈值与容许波动。

## 隐藏终端初始化修复：2026-09-15

终端视图与面板同时可见时，才自动请求 shell 配置、创建首个进程并加载活动实例的 xterm。
隐藏期间工作区变化不触发初始化；已有实例保留输出，首次显示时再加载渲染器。并发激活共用
正在进行的配置请求；等待期间隐藏或销毁视图不再创建进程，用户移走焦点后完成初始化不抢焦点。
本批未修改分包规则。

沿用上文环境与脚本，正式 Web 产物三次复测中位数：

| 场景 | 操作到就绪 | 主线程脚本 | 主线程任务 | 此阶段已观测完成的响应字节 |
| --- | ---: | ---: | ---: | ---: |
| 启动 | 819 ms | 113 ms | 212 ms | 3.916 MB |
| 首次代码 | 192 ms | 97 ms | 184 ms | 37.5 kB，另有两个 worker 请求未计入 |
| 首次 PDF | 279 ms | 109 ms | 172 ms | 428.2 kB，另有 PDF worker 请求未计入 |
| 显示终端 | 82 ms | 12 ms | 48 ms | 348.1 kB |

- 启动已观测响应字节减少约 348 kB；xterm 请求确定移至首次显示终端阶段。
- 首次终端就绪从 50 ms 增至 82 ms；延迟加载确实把部分等待转移到首次使用。
- 启动时间从 839 ms 到 819 ms；仅三次本机采样，不能据此认定普遍的启动耗时收益。
- 8 个终端 Playwright 集成测试通过，覆盖隐藏与视图切换、重复激活、隐藏/销毁竞态、焦点、早期输出和首次输入；正式产物加载测试三次通过。
- Renderer 类型检查、浏览器测试编译及正式 Web 构建通过。验证未覆盖 Electron；测试日志仍有环境同时设置 `NO_COLOR` 和 `FORCE_COLOR` 的提示，不影响上述结果。

## 终端可见性与焦点契约

- 终端视图位于 `src/ash/workbench/contrib/terminal/browser/terminalView.ts`，与 VS Code 对应文件一致；注册入口和测试使用此路径。
- `ViewPane` 提供 `isBodyVisible()`、`onDidChangeBodyVisibility` 和 `setExpanded()`；内容区可见性由宿主可见状态及展开状态共同决定。
- `CompositePart` 将布局可见状态传给活动视图容器。终端消费 ViewPane 的事件，不再单独组合面板与视图状态。
- 仅显示终端保留编辑器焦点。明确调用 `focus()` 或新建终端时才请求聚焦；等待期间隐藏、销毁或移走焦点会取消该请求。
- `ViewPaneContainer.openView(id, focus?)` 展开目标视图，只有显式要求时才聚焦；已存在的视图不会被重复注册。
- 终端容器尺寸为零时不调整进程行列数，避免隐藏和重开期间把输出挤出可见区。新建和重新启动操作以稳定的窗格节点保存焦点请求，用户移走焦点后不会抢回。
- 上述签名及行为依据本地 VS Code 源码核对；这不代表整个终端服务 API 已对齐，也未执行 VS Code 与 Ash 的双端运行比较。

### 本批补充验证

- 13 个终端浏览器集成测试、3 个视图单测通过。
- 新增同一条 Web / Electron App Server 端到端测试：隐藏启动、真实 shell 输入、隐藏后保留输出、重开不重复创建、新建第二个终端聚焦；两端均通过。
- Electron 正式构建、Web 正式构建及相关类型检查通过。
- Electron 验证途中两次在工作台出现前触发 30 秒启动超时；同一构建重跑后通过。尚未定位启动耗时波动，不能据一次通过认定其已解决。
- 日志仍有同时设置 `NO_COLOR` / `FORCE_COLOR` 的环境提示；没有通过放宽断言或延长测试超时来消除失败。

## 接线整改范围

代码编辑器 Pane 的文本模型、语言功能、语言配置和实例化服务改为构造注入；语言服务不再
通过 Workbench、EditorPart、EditorGroup、Pane 创建参数逐层传递。浏览器编辑器创建入口不再
自建替代容器，缺失必需注册在创建阶段报错。单测与浏览器集成测试使用同一实例化机制。

这不是全仓库依赖注入迁移；其他 Pane 和代码编辑器剩余服务的创建职责没有在本轮全面整改。
